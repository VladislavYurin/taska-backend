# Unpaid creation closure — TAS-478

Paid creation has one immutable UTC deadline, captured by `CreateTenant` (default 30 days). `TenantCreationLifecycle` serializes expiry, owner cancellation and the first-payment decision on the tenant row, then the provisioning operation. Lifecycle, version/restriction version, append-only receipt, routing completion and outbox are committed together. FREE admission, memberships, global identity and financial records are retained. Renewal expiry is outside this transition.

## Commands and scheduling

`TenantService.CancelTenantCreation` preserves the blueprint request: `ConfirmedAction.confirmed=true`, UUID idempotency key and required positive decimal `expected_version`. An active owner with `TENANT_ADMIN` membership and an ordinary web session may cancel unpaid `AWAITING_PAYMENT` or `AUTO_CLOSED`. Global web sessions use a narrow local SQL scope for that one command; it cannot be forwarded as tenant authority. Matching tenant web sessions are also accepted. PAT, OAuth, service credentials, another tenant, non-owner and missing session cannot cancel. Global admin status gives no bypass. Receipt replay rechecks current ownership/membership and returns the original result; changed input under the same key is `IDEMPOTENCY_CONFLICT`. Missing/stale versions produce `VERSION_CONFLICT`, missing confirmation produces `CONFIRMATION_REQUIRED`.

The scheduled expiry worker reads at most 20 due tenant IDs from the minimal dispatch index, obtains online-authorized tenant-service authority for each attempt, and rechecks the original deadline and unpaid PAID state under the row lock. At or after the deadline it closes as `AUTO_CLOSED` / `AUTO_EXPIRED`; a confirmed owner cancellation closes as `OWNER_CANCELLED` / `OWNER_CANCELLED`. The optional Tenant fields `creation_closure_reason` (13) and `creation_closed_at` (14) expose the distinction. Repeated expiry/cancellation has one lifecycle/outbox effect. A new invoice or provisioning retry never reopens a closed company or changes its deadline. Create a separate company for a new attempt.

`taska.tenant.creation-expiry-poll-ms` controls the Spring reactive scheduler interval (default 1000 ms). Routing IDs/timestamps grant no data access. Missing runtime trust leaves the worker idle. Its internal RPC `ExpireTenantCreation` requires a verified matching tenant, SERVICE credential, tenant-service issuer, exact action and write scope, with the normal mTLS/JWS/replay/online-authority checks.

Hard cancellation fences and stops a pending provisioning operation. Automatic closure fences stale acknowledgements, but private preparation may finish without opening the company. Finalization uses the same tenant→operation lock order and keeps `AUTO_CLOSED` closed. No cleanup, refund or destructive compensation occurs here.

## First-payment boundary

`ApplyTenantInitialPaymentDecision` is service-only for billing-service and accepts only tenant/decision IDs. `TenantCreationDecisions.Authority` resolves the immutable primary financial decision outside the SQL transaction. It must certify the financial fact, matching creation operation/plan/invoice, full receipt of funds and an already committed GRANTED coverage ID. No browser success flag, amount or client timestamp can activate a tenant. Until TAS-352 supplies the production authority, the default provider returns `DEPENDENCY_UNAVAILABLE`; fake financial decisions exist only in tests.

The lifecycle hook accepts only full payment for the original creation, received by the earlier of the invoice deadline and original creation deadline (inclusive). Exact timestamps are compared directly. A DAY observation represents a half-open interval; one crossing the deadline remains `NEEDS_EVIDENCE`. Partial, late or unmatched decisions cannot activate; missing committed coverage also requires evidence. The authority's complete-funds observation must account for every contributing payment; an early partial payment is insufficient.

A timely full decision arriving after automatic closure may restore that company. If both preparation checkpoints have succeeded, it activates immediately; otherwise it records immutable first-payment references and waits in `AWAITING_PAYMENT` until provisioning finishes. An accepted first payment prevents later unpaid expiry. `OWNER_CANCELLED`, `DELETING` and `DELETED` are never restored. Same decision is replayed; changed evidence for that immutable ID conflicts; the same financial fact under another decision creates no additional effect. Settlement, actual period grants, PSP/bank integration and late-money reconciliation remain TAS-352/361/378 and related financial tasks.

The existing tenant member directory applies this guard after actor/membership authorization. Registry/operation metadata and cancellation remain accessible. The gateway and project/workflow adapters must apply the same policy when those B2B routes are activated; this change does not publish new legacy REST routes.
