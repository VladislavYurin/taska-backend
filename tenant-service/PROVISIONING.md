# Company provisioning — TAS-337

`CreateTenant` atomically persists the registry row, owner membership, lifetime FREE admission, `tenant_operations`, routing entry and creation outbox event. The response and every idempotent replay read the actual operation state; response-cache expiry never replaces its durable identity. Names follow the 120-code-point blueprint limit; name validation and unavailable plan errors carry the field name in safe error metadata. Tenant DTO adds optional `planVersionId`, `creationOperationId` and `creationKind` (wire fields 10–12).

## Execution and recovery

The scheduled worker reads at most 20 due routing IDs, then obtains an online-authorized SERVICE context for each tenant. The routing table contains only tenant/operation IDs and scheduling timestamps. It confers no tenant authority. Data, immutable inputs, step checkpoints and leases remain in the FORCE RLS `tenant_operations` table. There is no product feature toggle for creating companies.

A local transaction claims a 30-second lease and advances a fencing token. Each network call occurs after that transaction has committed; no SQL connection is retained across RPC. The accepted operation snapshots its plan version, FREE/PAID kind and published default workflow template version. Steps are:

1. Copy the immutable private workflow template. The workflow owner records `(tenantId, operationId)` and rejects altered template input on retry. No fake project or mutable workflow instance is created.
2. Initialize one billing subscription/account using the stable `operationId:BILLING` receipt. The immutable accepted published plan remains usable even after a newer offer is published. FREE has no paid period; PAID stays `AWAITING_PAYMENT`. PSP customers are not created here.
3. In one tenant transaction, verify both checkpoints and active owner/admin, update lifecycle (`ACTIVE` for FREE, `AWAITING_PAYMENT` for paid), mark the operation `SUCCEEDED`, append `TenantProvisioned` and complete the routing entry.

Owner membership is the initial participant baseline. Global settings remain in the versioned platform registry; no per-company flag overrides are introduced. Ongoing quota reservations/enforcement and entitlement projections belong to TAS-322/319 and their consumers.

A crash or cancellation leaves the operation leased until expiry. The next worker resumes with the same business keys; a lost successful response can repeat a remote call but cannot create a second account or template. A stale worker cannot checkpoint or finalize after another claim advances the fence. Transport/unknown failures keep `RUNNING`, save only `DEPENDENCY_UNAVAILABLE` and retry after five seconds. No exception message or response body is stored. A bare gRPC status (including FAILED_PRECONDITION/INVALID_ARGUMENT/ALREADY_EXISTS) remains retriable because it does not prove a deterministic business rejection. Locally established invalid input/state conflicts produce terminal `FAILED/INVALID_STATE` for operator investigation, without activating FREE, restoring its consumed eligibility, deleting the global account or modifying another company. There is no public terminal-operation reset or automatic destructive compensation.

Paid creation keeps its original immutable UTC deadline (default 30 days). Provisioning never grants paid coverage, starts autopay, extends the deadline or changes pending-first-payment restrictions. Cancellation/auto-close is TAS-478; confirmed payment activation is TAS-352. A concurrent lifecycle change prevents final activation.

## Transport and activation

`TenantService.GetTenantOperation` preserves blueprint request field numbers and returns only operation metadata. An active original creator can read with a global web session, or a matching tenant web session. Another creator, another tenant, missing session or PAT/OAuth gets an error. Global lookup uses a local read-only tenant scope; it cannot mint/forward a tenant credential. Public gateway HTTP/session adapters remain outside this foundation until the session/gateway integration is activated.

Internal `tenant-provisioning.proto` defines billing/workflow provisioning and service-only resume RPCs. Handlers require the verified tenant, exact action, `SERVICE` credential, `tenant-service` issuer and write scope. Server interceptors enforce mTLS SPIFFE identity and message-bound JWS with replay protection. The workflow `tenant-storage` profile enables only its provisioning RPC; ordinary workflow RPCs still require TAS-342.

To activate, supply real `RpcContextSecurity` keys/replay/online-authority providers, the existing identity/KMS/FREE-purpose providers, and mTLS Reactor stubs for `BillingService`, `BillingProvisioningService`, and `WorkflowProvisioningService`. Current offer resolution and provisioning use the production signed gRPC adapters. Missing providers fail closed; no test authority or plaintext fallback is installed. The worker resolves trust at poll time and starts consuming pending operations once the provider is available. `taska.tenant.provisioning-poll-ms` controls scheduling (default 1000 ms), not product availability.

## Migration and verification

Changeset 0006 appends the operation and minimal routing tables. It upgrades pending registry creations with their existing operation IDs and original plan/kind; no applied changeset is rewritten. During this one transaction, the owner temporarily removes FORCE only on the registry table for its migration read, then restores FORCE before commit. No runtime role gains bypass privileges. Workflow changeset 0013 appends an immutable tenant-scoped receipt table. Roll forward on an interrupted migration; do not drop operation/receipt history while remote effects may exist. Reverting binaries does not undo completed activation or release FREE eligibility; retain the new tables and use a verified database backup for destructive recovery.

Run `python3 scripts/harness.py check --module tenant-service`; its upstream reactor also exercises billing/workflow. Required reports include `TenantProvisioningIntegrationTest` and `TenantProvisioningRpcIntegrationTest`. The latter runs real production gRPC handlers with mTLS/JWS and three separate PostgreSQL/Testcontainers databases, loses acknowledgements after successful remote writes, runs the actual Spring-scheduled reactive worker again and checks one registry/membership/account/template, actual operation replay and unpaid isolation. Identity/FREE providers in this transport fixture are test authorities; the real lifetime ledger and its atomic registry admission are covered separately by `FreeEligibilityIntegrationTest`. Classes-only test artifacts keep each service’s Liquibase resources separate. Fixtures are automatically destroyed. It is a local service-path E2E, not a public HTTP, PSP or deployed-stage acceptance claim. The upgrade fixture also injects a duplicate operation during migration and verifies rollback restores FORCE RLS and removes partial DDL before a successful retry. Component suites additionally cover RLS, concurrent receipts, lease expiry, stale workers, immutable inputs and final-commit rollback.
