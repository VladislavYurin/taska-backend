# Design

## Context

ManagedRpcTrust.snapshot синхронно читает и заново десериализует весь JSON под одним monitor на каждом control/business вызове. Повторное создание коллекций увеличивает allocation пропорционально полному snapshot. Внешняя цепочка TAS-363 многократно вызывает этот путь. Причина проверяется JFR и сравнением одинаковых owned сценариев, а не одним успешным повтором; результаты остаются вне Git.

## Goals / Non-Goals

Цель — устранить повторную десериализацию и соответствующую нагрузку, сохранив fail-closed и проверку актуального файла на каждом вызове. Не менять deadlines, не добавлять слепые повторы записей, не кэшировать actor/grant/ACL decisions и не менять общую stage.

## Decisions

- Сначала читать текущий файл с прежним ограничением размера и считать digest. При совпадении с последним валидным содержимым использовать ту же проверенную модель; при изменении заново выполнять полный parse и structural validation.
- Temporal validation выполняется при каждом обращении, включая повторное использование. Новый невалидный файл, отсутствие файла, rollback и замена bytes при той же generation завершаются отказом.
- Snapshot, services, keys, edges и вложенные collections неизменяемы. Наружу не выдаётся объект, который может изменить последующие решения.
- Signing material, действительность ключа, точный grant, primary authority и replay продолжают проверяться как раньше. Сетевые вызовы и транзакционные границы не меняются.
- E2E сохраняет method, нормализованный path, status и duration в приватный report; без query/body/headers/credentials. Это диагностика, а не ослабление HTTP assertions.

## Risks / Trade-offs

Общий компонент затрагивает все RPC. Нужны security regression, полная CI-матрица и повторные owned REST/mTLS E2E. Размер единственной модели ограничен прежним пределом файла 1 МБ; содержимое файла читается заново, last-known-good fallback при недоступности не допускается.
