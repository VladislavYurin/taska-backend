# Telegram-уведомления Taska: подключение и устройство

## Как пользователь подключает Telegram

1. Открывает **Settings → My profile → Notifications**.
2. Включает или выключает **Email**. Адрес берётся из учётной записи Taska, изменить получателя здесь нельзя.
3. Нажимает **Connect Telegram** и переходит по выданной персональной ссылке к боту.
4. Нажимает **Start** в личном чате с ботом. Само это действие ещё не включает рассылку.
5. Возвращается в профиль Taska, проверяет имя найденного Telegram-аккаунта и нажимает **Confirm account**.
6. После подтверждения Telegram включается. Email сохраняет прежний выбор: для обоих каналов оставить оба переключателя включёнными, для Telegram без почты выключить Email. Оба выключены — остаётся inbox в Taska.

Ввод `@username`, телефона или `chat_id` не нужен. Username необязателен и может меняться; получателем служит подтверждённый числовой ID личного чата. Одноразовая ссылка действует 10 минут; перевыпуск отменяет прежнюю. Ссылку не следует передавать другим людям. Подтверждение в авторизованном профиле защищает от случайно пересланной ссылки. Одновременно один Telegram-аккаунт привязан только к одному пользователю Taska.

**Disconnect** в профиле и `/stop` у бота разрывают привязку и отменяют ожидающие Telegram-отправки. Выключение переключателя сохраняет привязку, но отменяет ожидающие задания канала. Уже переданный SMTP/HTTP-запрос может закончиться после отключения. После переподключения старая очередь на новый аккаунт не уходит.

Приглашения для активации учётной записи остаются отдельными email-письмами: до активации у человека ещё нет подтверждённого Telegram.

## Создать тестового бота

1. В Telegram откройте проверенный [@BotFather](https://t.me/BotFather).
2. Отправьте `/newbot`, задайте имя, например `Taska Notifications Test`, и свободный username, заканчивающийся на `bot`, например `your_taska_test_bot`.
3. Сохраните выданный token в менеджере паролей. В репозиторий, Jira и чат его не копировать. Отдельный бот для тестового стенда не затронет другие интеграции.
4. В `/setjoingroups` запретите добавление бота в группы. Код всё равно принимает команды привязки только из личного чата.
5. Username и token понадобятся в конфигурации ниже. Фотография и описание необязательны; `/setdescription` можно задать текст «Уведомления Taska. Подключите бота в настройках своего профиля».

[Официальное создание бота](https://core.telegram.org/bots/tutorial#obtain-your-bot-token).

## Подключить к проекту

Сначала развернуть backend и UI TAS-387. Миграции применяет notification-service автоматически. Потребуются обновлённые **api-gateway**, **notification-service**, **admin-service** (маскирование новых полей) и UI. В существующей общей конфигурации Compose/Dokploy задать:

```dotenv
NOTIFICATION_TELEGRAM_ENABLED=true
NOTIFICATION_TELEGRAM_BOT_USERNAME=your_taska_test_bot
NOTIFICATION_TELEGRAM_BOT_TOKEN=значение_из_BotFather
NOTIFICATION_TELEGRAM_WEBHOOK_SECRET=случайный_секрет_от_32_символов
NOTIFICATION_APP_URL=https://taska.ozero.dev/#
NOTIFICATION_DELIVERY_ENABLED=true
```

Секрет webhook — случайное значение длиной 32–256 символов из `A-Z a-z 0-9 _ -`, отличное от bot token. Создайте его менеджером паролей. У gateway и notification-service значения ENABLED и WEBHOOK_SECRET должны совпадать. Username вводится без `@`. URL приложения нужен с `/#` для текущего hash routing. Вне localhost используется HTTPS.

Используйте git-ignored `.env` или secret storage Dokploy. Шаблон `.env.docker.example` не содержит настоящих секретов. После изменения конфигурации пересоздайте gateway и notification-service. При выключенной Telegram-интеграции её секреты не нужны; email/inbox продолжают работать.

Для Email заголовок `From` по умолчанию берётся из `NOTIFICATION_MAIL_USERNAME`. Если SMTP использует другой разрешённый адрес отправителя или логин провайдера не является email, задайте `NOTIFICATION_MAIL_FROM`. Это относится и к рабочим уведомлениям, и к приглашениям; SMTP-адрес должен быть разрешён вашим провайдером.

Затем зарегистрировать webhook, запустив из корня backend:

```bash
python3 scripts/configure-telegram-bot.py --env-file .env \
  --webhook-url https://api.taska.ozero.dev/api/v1/integrations/telegram/webhook
```

Если конфигурация хранится только в Dokploy, можно опустить `--env-file`: скрипт спросит token и webhook secret скрытым вводом. Укажите тот же secret, что в проекте. Задайте username в окружении для проверки соответствия бота. Скрипт вызывает `getMe`, проверяет username, задаёт `/start`, `/help`, `/stop`, вызывает `setWebhook` и проверяет `getWebhookInfo`. Он не печатает token, secret и содержащие token URL, не очищает накопленные updates и не отправляет тестовые уведомления пользователям.

Для локального тестирования Telegram должен достучаться до публичного HTTPS gateway: нужен тестовый стенд или HTTPS tunnel к локальному gateway. Обычный `localhost` для webhook недоступен Telegram. Не включать параллельно `getUpdates` и webhook на одном боте. Входящие запросы имеют ограничение 32 KiB и проверяются по secret header; бизнес-API остаются под JWT. gRPC-порты должны оставаться во внутренней сети: это существующая доверенная граница Taska.

## Проверить вручную

1. Открыть Notifications при Telegram выключенном на сервере: Email доступен, Telegram честно сообщает о недоступности.
2. Включить серверную конфигурацию, обновить профиль, подключить и подтвердить тестовый личный аккаунт.
3. Назначить пользователю задачу **от другого аккаунта**: собственные действия могут отсеиваться существующими правилами получателей. Проверить inbox и сообщения.
4. Последовательно проверить Email only, Telegram only, оба канала и оба выключены. Для email нужен работающий SMTP.
5. Проверить кнопку открытия задачи на hash URL, отключение переключателя, Disconnect, `/stop`, истёкшую ссылку.
6. Заблокировать бота в Telegram и создать новое событие: почта/inbox сохраняются, в профиле Telegram станет недоступен после постоянного отказа API. Разблокировать, отключить старую привязку и подключить заново.

Настоящая отправка и настройка webhook требуют вашего тестового бота. Автотесты используют mock Telegram/SMTP и PostgreSQL/Testcontainers.

## Где хранятся данные и как доставляются сообщения

Все данные каналов принадлежат **notification_db**, схеме `taska`:

| Таблица | Назначение |
| --- | --- |
| `notification_preferences` | Выбор Email/Telegram, email из проверенного auth-контекста, подтверждённые Telegram user/chat ID, имя, bot username, версия каждого канала, безопасный код ошибки. |
| `telegram_link_requests` | Одна текущая заявка пользователя, SHA-256 token hash, TTL, одноразовое потребление `/start`, кандидат для подтверждения. Raw token не сохраняется. |
| `telegram_updates` | Дедупликация `(bot_username, update_id)` без raw Telegram payload. Retention 7 дней. |
| `notification_deliveries` | Отдельное durable задание на пару notification/channel, попытки, lease, время повтора и безопасный код ошибки; также ответы на команды боту. |
| `notification_channel_throttle` | Общий для всех экземпляров лимит отправки Telegram. |

Для новых пользователей preferences создаются из `UserActivated`. Для существующих синхронизируются из проверенного контекста при `/users/me` (ограниченная фоновая очередь, без ожидания в ответе профиля) и открытии настроек; явный выбор email при этом сохраняется. Повторный GET настроек с тем же проверенным email только читает БД. Ответ создания ссылки дополнительно содержит `preferences` — согласованный снимок, позволяющий UI обойтись без немедленного GET. При rolling upgrade поле может отсутствовать. Миграция не создаёт отправок из старой истории.

Kafka handler атомарно сохраняет dedup marker, inbox и задания доставки. Workers отдельно отправляют EMAIL и TELEGRAM после commit; недоступный канал не блокирует другой. Повторное Kafka-событие не создаёт второе задание. По умолчанию 8 попыток, exponential backoff до часа, lease 2 минуты и восстановление зависших workers. Telegram 429 учитывает `retry_after`; 400/403 останавливают отправки этой привязки. Ошибки провайдера/SMTP и token-содержащие URL не сохраняются и не логируются. Admin read-only скрывает token hashes и идентификаторы личных чатов.

Выбор канала и его версия проверяются перед сетевой отправкой. Изменение получателя, opt-out и перепривязка делают старые задания недействительными. Успешный второй канал не переотправляется из-за отказа первого. Отдельная очередь приглашений и её история сохраняются.

Telegram отправляется простым текстом без parse mode, с безопасным представлением уведомления и frontend-кнопкой для существующей задачи. Тексты комментариев повторно не загружаются. Консервативный общий лимит — один запрос в 1,1 секунды на всю установку; это покрывает и личный лимит чата. Для крупной установки этот лимит можно развить в отдельные bucket по боту/чату. Ответы на команды старше часа отменяются; housekeeping очищает истёкшие заявки спустя сутки.

Внешние SMTP/Telegram не обеспечивают exactly-once: при timeout после принятия запроса провайдером возможен повтор. Это не потеря durable задания; ограниченные повторы предпочтительнее молчаливого пропуска. Метрики `taska.notification.delivery`, `taska.notification.queue.depth`, `taska.notification.queue.age.seconds` не содержат ID чатов и секретов.

Контракты: [OpenAPI](../api-gateway/src/main/resources/static/openapi.yml), [protobuf](../grpc-common-lib/src/main/proto/v1/notification-settings.proto). Telegram: [deep links](https://core.telegram.org/bots/features#deep-linking), [webhook](https://core.telegram.org/bots/api#setwebhook), [sendMessage](https://core.telegram.org/bots/api#sendmessage).
