# Архивирование и восстановление проекта

Native `tenant-storage` реализует `DELETE /api/v1/projects/{projectId}` и `POST /api/v1/projects/{projectId}/restore`. Версия возвращается как decimal string `ProjectResponseDto.version`; историческая версия проекта начинается с нуля. Обе команды требуют strong quoted `If-Match: "0"` и canonical lowercase UUID `Idempotency-Key`. Отсутствие версии даёт 428 VERSION_CONFLICT, устаревшая версия с новым ключом — 412, конфликт payload под прежним ключом — 409 IDEMPOTENCY_CONFLICT. Legacy DELETE без новых заголовков сохраняет прежний контракт; restore активирован только native профилем.

Перед каждым новым запросом и повтором проверяются текущие primary identity/membership, tenant/project ACL и lifecycle/policy. OWNER/TENANT_ADMIN имеет эффективную ADMIN роль без project membership; аккаунт GLOBAL_ADMIN сам по себе не даёт доступа — нужен проверенный административный путь/MFA или scoped grant и аудит. Защита последнего project ADMIN сохраняется.

В локальной транзакции project lock сериализует изменения. Изменение archived_at увеличивает version и добавляет tenant outbox (`ProjectArchived` с прежним payload либо `ProjectRestored` с projectId/restoredBy/restoredAt). Квитанция сохраняет protobuf-ответ вместе с tenant/actor/authority/key и payload. Повтор возвращает этот ответ после текущей авторизации и не повторяет эффект, даже если проект позднее восстановлен. Новый ключ с актуальной версией для уже достигнутого состояния сохраняет ответ без события/увеличения версии. Снятие архива не меняет UUID, историю, настройки или квоту; удаление и освобождение квоты относятся к TAS-459. Новая migration добавляет append-only RLS receipts; прежние changesets не переписываются.

Сценарий `project_lifecycle_e2e.py` описан в [каталоге E2E](backend-e2e-scenarios.md); состав проверок — в [матрице](../agents/verification.md). Событие восстановления не включает текст задач и не вводит новый пользовательский канал уведомлений.
