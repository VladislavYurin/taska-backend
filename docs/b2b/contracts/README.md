# B2B contracts — TAS-305 / TAS-470 / TAS-471

Это нормативный blueprint для implementation, а не действующий API. Проверенный код: `af7ab57ead44304b89bbd47dabeeba45b761ce16`; решения: [актуальная бизнес-спецификация](../ai-business-spec.md), включая уточнения владельца от 03.11.2026. [Инвентарь baseline](../api-inventory.md) отделён от [целевого OpenAPI](b2b-openapi.yaml) и [целевого proto](b2b.proto). Согласованные модели: [данные](../target-data-model.md), [матрица доступа](../access-control.md), [async/files](../async-and-files.md), [retention ES_V1](../retention-policy.md) и [policy JSON](../schemas/retention-policy.json). Ни static OpenAPI, ни `grpc-common-lib/src/main/proto/v1`, ни generated code этой аналитикой не изменяются.

OpenAPI содержит 86 операций на 75 paths, 122 именованные schemas; основные DTO закрыты `additionalProperties: false`. Proto содержит 94 RPC: REST orchestration + 3 quota authority + access decision + entitlement lookup + verified payment ingress + project-quota read с project ACL + append-only payment evidence refinement + 3 unmatched wire intake/list/assignment RPC. Названия, поля и номера определены; coding tasks реализуют этот контракт, а не повторяют аналитическое «согласовать API». Политика действия обязательна вместе со схемой: формат сам не доказывает права или финансовый факт.

## 1. Идентификаторы, даты, деньги и версии

UUID — canonical lowercase UUID string; сервер генерирует resource/operation IDs. `userId` глобален, `tenantId` — одна компания. В маршруте tenant обязателен для управления компанией; существующие проектные/issue routes получают выбранный tenant из проверенного credential. Несовпадающие URL/header/body/resource IDs никогда не переключают tenant.

Даты — RFC3339 UTC с `Z`, точность до микросекунд; ISO даты без timezone для финансовых фактов запрещены. Периоды `[startsAt, endsAt)`; ровно `endsAt` покрытие закончилось. Сохраняются `anchorDay` и точный UTC момент: 31 января → последний день февраля → 31 марта. `occurredAt` (верифицированное фактическое поступление), `observedAt` (обнаружение системой), `confirmedAt` (ручное/провайдерское подтверждение) — разные факты. `occurredPrecision=EXACT` требует `occurredAt` без интервала. При `DAY` поле `occurredAt` отсутствует/null; обязательны `occurredNotBefore` и `occurredBefore` с upper>lower. Это полуоткрытый UTC-интервал, восстановленный из подтверждённой даты/часового пояса выписки, а не выдуманная точная полночь. Если весь интервал до deadline — факт своевременный; если весь строго позже — поздний; пересечение границы остаётся NEEDS_EVIDENCE/MANUAL_REVIEW без автоматической активации или ложного late/refund. Точное значение, пришедшее позднее, добавляется immutable FinancialEvidenceRefinement; исходный денежный факт и его DAY evidence не изменяются.

Деньги — `Money {amountMinor: "2000", currency: "EUR", exponent: 2}`, целое неотрицательное число в minor units, без float. EUR/USD exponent строго 2. Подписочный invoice не принимает сумму от клиента: сервер берёт immutable plan snapshot. Ledger debit/credit хранится отдельным направлением; отрицательное Money не используется. Итог net+tax=total проверяется точной арифметикой; ставки/налоговые правила берутся только из provisioned commercial profile, не из предположения о продавце. `FxQuote` фиксирует decimal rate, source, observedAt/expiresAt; старый invoice не пересчитывается. Нет свежего утверждённого FX — новый USD invoice получает `POLICY_NOT_CONFIGURED`/503; EUR только после явного нового выбора. Запуск только в EUR не утверждался; USD остаётся частью target capability и включается при готовых merchant/method/FX source и freshness configuration, без скрытой смены валюты.

Счётчики storage/lifetime/versions передаются decimal string, чтобы браузер не терял int64 precision; допустимый backend диапазон 0..9223372036854775807. Версия начинается с 1. `If-Match: "17"` — strong entity version, missing→428, mismatch→412. При нескольких агрегатах блокировки идут по `(tenantId, aggregateKind, aggregateId)`, проверяется актуальное состояние внутри транзакции владельца. Исключение `confirmWireReceipt`: это идемпотентная команда сверки immutable receipt, поэтому `If-Match` и `MutationOptions.expected_version` не требуются; у `PaymentFact` нет изменяемой entity version, а `schema_version` не является токеном конкурентности. Перед финансовым эффектом billing-service берёт source-payment/invoice locks в установленном порядке и заново проверяет verified evidence, eligibility и текущие allocation/coverage; durable dedupe не допускает повторного эффекта. При stale/несогласованном состоянии команда возвращает соответствующий `INVALID_STATE`/409 или `MANUAL_REVIEW`, а не требует недоступную клиенту версию.

Для `setAutopayConsent` precondition — `Subscription.version` из `GET /api/v1/tenants/{tenantId}/billing/subscription`, а не `AutopayMandate.version`. Родительская subscription существует до первого consent; отсутствие mandate допустимо, отсутствие самой subscription → `INVALID_STATE`/409 без выдуманной версии. Под subscription row lock повторно проверяются версия, текущий owner и admission fences; изменение mandate и увеличение `subscriptions.version` выполняются в одной локальной транзакции с outbox/idempotency result. Неуспех не меняет ни mandate, ни version. Перед следующей командой клиент снова читает subscription; версия mandate из ответа не заменяет родительский precondition. `x-version-source` у versioned command задаёт operation/schema/property для этого чтения.

Для `changeGlobalAccount` и `adminDeleteAccount` precondition берётся из `GET /api/v1/admin/accounts/{userId}` → `AdminAccount.version`. Это decimal projection **целевой** `auth-service.taska.users.account_version` (bigint, initial1, положительная); в baseline колонка ещё не реализована. Auth-service под lock пользователя проверяет текущую версию и увеличивает её в той же транзакции при фактическом изменении global_role/status/deleted_at любым writer, включая логическое удаление; retry/no-op не увеличивают её повторно. Timestamp, session generation и schema_version не подменяют account version. Для удаления `payload.expectedAccountVersion` обязан равняться числу внутри `If-Match`; расхождение → `VALIDATION_FAILED`/400, stale current version → `VERSION_CONFLICT`/412, отсутствие header →428. Проверки owner/last-admin, fence и revoke остаются обязательными. GET возвращает только userId/role/state/version, не profile PII; secret и command bodies не логируются. Read-модель включает исходные INVITED/LOCKED; это не расширяет допустимые business transitions команд. После purge account возвращается404; retained tombstone не восстанавливает identity и не выдаёт прежние email/displayName/avatar.

## 2. Credential и независимые web-сессии

`credential_kind`: `WEB_GLOBAL`, `WEB_TENANT`, `USER_PAT`, `USER_OAUTH`, `ADMIN_PAT`, `ADMIN_OAUTH`, `SERVICE`. `WEB_GLOBAL` позволяет список компаний, создание, выбор tenant и разрешённые личные действия; сам не даёт доступ к project data. `POST /api/v1/auth/tenant-sessions` создаёт отдельную refresh family для выбранной компании. Вкладка хранит свою пару sessionId/tenantId; server-side «общий выбранный tenant пользователя» не существует. Переключение вкладки не меняет другие web/PAT/OAuth grants.

Access JWT: `iss=taska-auth`, `aud=taska-api`, `sub=userId`, `sid`, `jti`, `kind`, `iat`, `nbf`, `exp`, `account_generation`; tenant-сессия дополнительно `tenant_id`, `membership_generation`. Tenant/global/admin claims валидируются online или по ограниченному read-cache; роль не авторизует без актуального состояния. JWT algorithm allowlist — EdDSA/Ed25519, `kid` обязателен, `none`/algorithm fallback запрещены. Секрет refresh — 32 random bytes, хранится SHA-256 digest; одноразовая rotation при успешном refresh, reuse отзывает именно family. Для конкурентного запроса используется тот же `Idempotency-Key`; retry возвращает прежнюю пару из краткого шифрованного response cache, а не вторую rotation. После утраты response cache тот же старый refresh не восстанавливается.

Новый login endpoint — `/api/v1/auth/web-sessions`; social login завершает тот же session issuer. Все старые `/auth/login`, OAuth social exchange/signup и OAuth AS `/login` обязаны либо делегировать этому issuer, либо отклонять неподдерживаемую B2B-сессию. Старый endpoint не оставляется обходом MFA/tenant scope. Старые access/refresh/PAT/OAuth без B2B scope на чистом запуске отзываются; отсутствие tenant никогда не означает «все компании».

`USER_PAT`/`USER_OAUTH` навсегда имеют один `tenantId`, `read`/`write` scopes; refresh не меняет binding. На каждой операции проверяются membership, project ACL, flags, entitlement, revocation. `write` включает возможность чтения, но не отменяет channel policy. Выпуск PAT — новый `/account/tenant-tokens`; legacy `/users/me/access-tokens` после rollout требует тот же explicit tenant DTO или прекращает выпуск, не оставляет unbound tokens. Метаданные/revoke остаются доступны при выключенном PAT-флаге. OAuth tenant явно выбирается в consent; code exchange и refresh сохраняют одобренный scope.

Обычные интеграции не изменяют displayName/avatar/password/email, не удаляют аккаунт и не выпускают PAT. Владение компанией не обходит D221. Tenant owner финансовые действия допустимы через user integration при `write`, flags и актуальных owner-правах; это не глобальное изменение аккаунта. MCP принимает тот же credential и не хранит расширенную authority в transport session.

## 3. GLOBAL_ADMIN, MFA и административный grant

После правильного первого фактора GLOBAL_ADMIN получает только `MfaChallenge`, без полноценного access/refresh. Email code обязателен и после social sign-in; pre-auth challenge нельзя обменять на tenant-session или использовать для выдачи grant. Код связан с `(challengeId, accountId, accountGeneration, ADMIN_LOGIN)` и hash; одноразовый consume и выдача сессии атомарны. Все решения D240/D242/D243/D245 сохранены: MFA требуется только GLOBAL_ADMIN; Telegram/TOTP не подменяют email второй фактор. Первичное подключение и recovery почты — аудируемая операторская процедура/другой действующий GLOBAL_ADMIN, без self-service bypass первым фактором.

`AdminScope.kind=TENANT_SET` требует непустой уникальный `tenantIds`; `PLATFORM` требует отсутствия списка. Пустой список не «всё». `level=READ|MODIFY`; `MODIFY` включает чтение. `manageGlobalAccounts=true` соответствует permission `accounts:manage` и допускается только `PLATFORM+MODIFY`. Условия D226 проверяются при block/global-role/delete-account и существующем admin profile/displayName update, независимо от tenant membership. User grant пользователя GLOBAL_ADMIN сохраняет обычные права; его роль не превращает USER_PAT в ADMIN_PAT.

Создание/расширение административных PAT/OAuth — только `ADMIN_WEB_MFA`; integration, даже platform+modify+accounts:manage, не может вызвать issue/expand endpoints. Replacement сохраняет actor, kind/client binding и требует свежий `If-Match`; изменение области/уровня/expiry инвалидирует старую grant generation. Отзыв выполняет полная web-сессия владельца grant/уполномоченного GLOBAL_ADMIN. Refresh не выпускает новый PAT и не повышает grant. Чтение имеет побочный служебный audit, это не требует MODIFY; mark-read notification/любая бизнес-запись требует MODIFY.

`x-policy` с суффиксом `WRITE` обычно означает mutation effect, а не имя enum grant level. Явное исключение — nonmutating `getGlobalAccount`: для чтения перед управлением аккаунтом повторно используется строгая `ADMIN_GLOBAL_ACCOUNTS_WRITE` authority. Нужен текущий ACTIVE GLOBAL_ADMIN с completed MFA web-session либо действующий administrative PLATFORM+MODIFY grant с accounts:manage; live role/account/grant проверяются до ответа. READ grant не повышается и этот endpoint им не открывается; служебный audit чтения не меняет аккаунт. Все `ADMIN_TARGET_*` требуют известный target tenant; его получают из проверенного ресурса и сверяют с областью grant. Неидентифицированный банковский приход не имеет tenant, поэтому record/list требуют PLATFORM. Полный административный bypass бизнес-квот/flags/restrictions действует только внутри предъявленной authority; integrity, audit, request signature, idempotency и доказательство оплаты не обходятся.

## 4. Trusted TenantContext и service identity

Новый `RequestContext` содержит существующий `Header` и новый `TrustedTenantContext`; `Header` не расширяется в blueprint. Baseline поля 1–4 и reserved поля `UserContext` сохранены. В implementation consumers переходят по сервисам; domain endpoint без проверенного контекста запрещается до открытия B2B traffic. Unmigrated consumers не получают совместимый «global tenant» fallback.

Внешние `X-Tenant-*`, `X-Actor-*`, forwarded role/scopes и client request context удаляются gateway. `requestId` нормализуется UUID, но не является authority. Сервисная проверка: mTLS peer identity из allowlisted SAN `spiffe://taska/<environment>/<service>` + подписанная Ed25519 JWS в gRPC metadata `x-taska-context`. `iss` равен вызывающему сервису, `aud` — точный recipient service, `contextVersion=1`; allowlist edge/service/action проверяется независимо от подписи. Ключи отдельны от пользовательских JWT и между средами; `kid` уникален; private key только у issuer, JWKS public keys по доверенному config.

JWS claims включают `iss`, `aud`, `iat`, `exp`, `jti`, `request_id`, `rpc` full service/method, `context_sha256`, `request_sha256`; hash — deterministic protobuf serialization полного RequestContext и полного RPC request соответственно. Assertion не входит в protobuf body, поэтому циклического hash нет. Любое изменение actor/tenant/action/body/path payload ломает подпись. TTL assertion ≤30s, clock skew ≤5s. `jti` используется один раз для mutations; retry получает новую assertion при том же business idempotency key. Issuer не может выбрать actor вне исходного проверенного grant: downstream delegation сохраняет actor/session/grant/generations и сужает service audience/action, не расширяет tenant scope.

`TrustedTenantContext` — название структуры, не автоматическое доверие wire-полям. Recipient interceptor до обработчика проверяет signature, mTLS peer=issuer, allowlist, hash, aud, expiry и scope; только затем помещает immutable context в Reactor Context. Нельзя доверять Header.node_id, входному protobuf user_id или global_role самим по себе. `SERVICE` actor допускает только allowlisted job purpose/resource; реальный initiating actor сохраняется отдельно, не выдаётся за текущего владельца.

Ротация ведётся отдельно для RPC assertions и auth access keys: publish новый public key → получить acknowledgement всех verifier текущей доверенной конфигурации → переключить signers и остановить old issuance → сохранять проверку old key не меньше максимального TTL реально выданных им credentials +5s skew после последней old issuance → удалить old key. Для RPC это максимум30s+5s, для auth access — его собственный максимум TTL+5s; фиксированные10min не заменяют acknowledgement/drain. Emergency kid revocation применяется немедленно, без routine drain. При JWKS outage допустимы только ранее доверенные ключи внутри hard trusted-config TTL; неизвестный kid всегда fail-closed, stale configuration не продлевается чтением. TTL задаётся валидируемой server configuration, а не временем жизни последнего запроса. Environment clock alert при drift>2s; tokens/assertions не логируются.

## 5. Применение политик, cache и отказ

Порядок: authentication → channel/grant scope → concealed resource lookup → актуальный account/membership/project ACL → lifecycle/capability → quota → version/confirmation. `GLOBAL_ADMIN` выполняет явную административную ветку, не неподписанный bypass. Owner/TENANT_ADMIN имеют project ADMIN во всех своих проектах; MEMBER/VIEWER сохраняют project ACL. Каталог action names из security matrix, например `tenant.transfer_ownership`, `membership.write`, `project.create`, `issue.update`, `billing.bank_confirm`, используется в `Capability.action` и assertion `action`; это закрытый реестр сервера, не вводимый клиентом permission.

Capabilities — объяснение текущего результата, а не разрешение на будущую запись. `policyVersion`, `entitlementVersion`, `membershipVersion`, `flagVersion` и hard expiry ≤30s включены в ответ. Invalidation событий немедленная, TTL никогда не продлевается чтением cache. Запись, выдача secret, скачивание, dequeue/job execution проверяют authority у владельца данных; outage→503 `DEPENDENCY_UNAVAILABLE`, без stale allow. Для ordinary reads допустим только неистёкший validated snapshot. Paid expiry проверяется по серверному UTC времени даже в cache.

Ограничения — независимый массив: `PAYMENT_EXPIRED`, `OVER_QUOTA`, `OWNER_PAUSE`, `PLATFORM_BLOCK`, `PAYMENT_DISPUTE`, `PENDING_FIRST_PAYMENT`. Оплата не удаляет чужие причины. Financial READ_ONLY сохраняет чтение, owner billing, tenant-admin member removal/invite revoke/project delete, self leave и принятие старого действующего invite. Owner pause/platform block запрещают invite acceptance; project-content read определяется отдельным глобальным флагом. Transfer/delete обычного владельца разрешены при owner pause, запрещены при platform block/open dispute; transfer требует current paid coverage+flag. Self-delete account после owner/last-admin checks не блокируется этими tenant restrictions (D249).

`x-policy` families: WEB_ACCOUNT — только обычная completed global/tenant web-session; TENANT_MEMBER — active membership либо explicit admin authority; TENANT_ADMIN — effective role; OWNER — current owner; EXPORT_ACTOR_CURRENT_ACL — creator plus повторная ACL/flag/lifecycle проверка; OPERATION_ACTOR_OR_ADMIN — только допустимый инициатор/админ области. В public invitation accept отсутствие web-session допустимо только для новой identity через проверенный invitation token; существующая identity требует authenticated same verified email, иначе 401/403 без раскрытия аккаунта.

## 6. HTTP ↔ gRPC errors

REST errors всегда `application/problem+json` с `Problem.code`, `requestId`, независимыми `reasons`; private identifiers/tokens/SQL/provider payload не попадают в title/violations. gRPC использует non-OK status + binary trailer `taska-error-bin` с `B2bErrorDetail`. Не возвращать 200 с error object. Таблица определяет status; unknown enum/поле отвергаются в boundary validation, неизвестная capabilities action не разрешается по умолчанию.

| HTTP | gRPC | Коды |
|---:|---|---|
| 400 | INVALID_ARGUMENT | TENANT_REQUIRED, VALIDATION_FAILED (невалидный формат/поле/cursor/header) |
| 401 | UNAUTHENTICATED | AUTHENTICATION_REQUIRED, TOKEN_REVOKED; MFA challenge сам не session |
| 403 | PERMISSION_DENIED | MFA_REQUIRED, SESSION_REQUIRED, SCOPE_DENIED, ADMIN_GRANT_REQUIRED, ADMIN_SCOPE_DENIED, MEMBERSHIP_INACTIVE, OWNER_REQUIRED, READ_ONLY, CAPABILITY_DISABLED |
| 404 | NOT_FOUND | RESOURCE_NOT_FOUND, TENANT_NOT_FOUND; чужой tenant/resource скрывается; known credential tenant mismatch в explicit selector: TENANT_MISMATCH/403 |
| 409 | ABORTED или FAILED_PRECONDITION | IDEMPOTENCY_CONFLICT, INVALID_STATE, LAST_ADMIN, OWNER_MEMBERSHIP_PROTECTED, FREE_ELIGIBILITY_USED, PAYMENT_PENDING |
| 412 | ABORTED | VERSION_CONFLICT при устаревшем If-Match |
| 422 | FAILED_PRECONDITION | QUOTA_EXCEEDED, INVITATION_EXPIRED, INVITATION_EMAIL_MISMATCH, CONFIRMATION_REQUIRED, CONFIRMATION_EXPIRED |
| 428 | FAILED_PRECONDITION | VERSION_CONFLICT при отсутствующем обязательном If-Match |
| 429 | RESOURCE_EXHAUSTED | RATE_LIMITED, Retry-After в секундах |
| 503 | UNAVAILABLE | DEPENDENCY_UNAVAILABLE, POLICY_NOT_CONFIGURED |

Для `ABORTED`: VERSION_CONFLICT→412, IDEMPOTENCY_CONFLICT→409. `RESOURCE_EXHAUSTED` используется только для временного rate/concurrency budget; business quota→FAILED_PRECONDITION/422. После auth validation чужой ID даёт одинаковый 404 независимо от существования; не возвращать причину billing/role чужой компании. Мутация с отказом не меняет данные, reserved quotas, financial allocations или idempotency success result.

## 7. Идемпотентность, concurrency и pagination

Все новые HTTP mutations требуют UUID `Idempotency-Key`; request_hash=SHA-256 canonical JSON + operationId + explicit resource IDs, scope `(actorId, credential authority, targetTenantId or GLOBAL, operationId, key)`. Replay повторно проверяет текущий доступ, затем возвращает прежний resource/result; удалённое membership не получает старую private response. Тот же key с другим hash→409. In-progress operation→202 с тем же Operation ID; transient до durable acceptance допускает retry, после acceptance resume одной операции. Нельзя обходить durable uniqueness новым key: payment source references, subscription logical period, invitation reservation, quota resource operation IDs имеют отдельные unique constraints.

Response-cache TTL 24h (обычные операции), encrypted secret-result cache 60s (login/refresh/PAT). Истечение cache не снимает durable dedupe/ledger uniqueness. Финансовые записи/доказательства/retention по O09; технический TTL не разрешает удалить ledger. Replay секретной выдачи после 60s→409 `INVALID_STATE`, повторная выдача требует нового подтверждённого flow; старый secret не извлекается из digest. Не логировать request bodies auth/confirmation/checkout.

GET lists используют opaque cursor (HMAC, bound actor+tenant+grantGeneration+filters+sort, expires 15min); limit default50, max100. Стабильный порядок `(createdAt,id)` ascending, где сущность не имеет createdAt — `(id)`; nextCursor отсутствует на конце. Cursor другого scope→400, отзыв права→403/404 прежде перечисления. `nextCursor` — ключ продолжения, не bearer authority. Для ключей allowlist сортировки фиксирован контрактом; пользовательский SQL sort expression не принимается. Поиск/агрегаты baseline остаются со своими текущими query DTO, но tenant predicate применяется до pagination/count.

## 8. Tenant, membership, invitations и quota authority

Tenant lifecycle: `PROVISIONING`, `AWAITING_PAYMENT`, `ACTIVE`, `AUTO_CLOSED`, `OWNER_CANCELLED`, `DELETING`, `DELETED`. Позднее подтверждение своевременной полной первой оплаты может восстановить только AUTO_CLOSED по D216, никогда OWNER_CANCELLED. Creation deadline snapshot — 30 суток default, новый invoice/retry не двигает. FREE consumption unique для подтверждённой email identity; удаление не восстанавливает право.

Membership `ACTIVE/SUSPENDED/REMOVED`; invitation — отдельная сущность, не membership без identity. Один owner и хотя бы один active TENANT_ADMIN защищаются в одной tenant transaction. Suspend/remove revoke отправленные pending invitations и access generations; cleanup assignments использует versioned compare-and-clear. Reactivate suspended TENANT_ADMIN возвращает MEMBER; новые project grants/assignments вручную. Invitations reserve ровно одно seat, TTL snapshot7d; resend не продлевает expiresAt и не создаёт резерв. Accept atomically converts reservation, skipped project grants перечисляются в ответе; owner pause/block запрещают accept, финансовый READ_ONLY допускает старое приглашение.

Quota RPC не имеет публичного REST endpoint. Только allowlisted resource-owner services вызывают Reserve/Commit/Release. Удалённый `kind`: только SEAT, PROJECT, STORAGE_BYTES — tenant. TASK_LIFETIME — локальный счётчик issue-service по projectId: проверка лимита, increment, создание issue и его outbox находятся в одной транзакции issue DB, remote reserve для него запрещён. Tenant quota snapshot содержит только агрегаты SEAT/PROJECT/STORAGE_BYTES; project-specific TASK_LIFETIME выдаётся через `/tenants/{tenantId}/projects/{projectId}/task-quota` с project ACL и не авторизует create. `quantity>0`, `actualQuantity<=reserved quantity`; storage подтверждается по реальному pinned object size, не данным клиента. Для project/seat commit quantity фиксируется reservation. Ключ resource operation unique, повтор commit/release идемпотентен; committed reservation нельзя отменить обычным release; освобождение доменного ресурса — отдельный подтверждённый cleanup с dedupe. Race reserve/commit/expiry решается lock+version одной записи владельца.

Default reservation TTL15min; upload presign≤5min. Expiry не освобождает quota вслепую при UNKNOWN downstream outcome: authoritative resource existence/operation journal проверяется reconciler, который COMMIT либо RELEASE; пока owner недоступен reservation остаётся accounted и требует retry. GLOBAL_ADMIN bypass увеличивает честный used counter и может дать OVER_QUOTA обычным участникам. Archived projects всё ещё counted; только irreversible project cleanup освобождает project/storage/seat где применимо, но lifetime tasks не уменьшаются от task delete.

Снятие собственной паузы компании — `DELETE /api/v1/tenants/{tenantId}/pause` (`resumeTenant`), без тела. Это явная команда владельца с обязательными `Idempotency-Key` и `If-Match`, ответами 412/428 для несовпавшей/отсутствующей версии; новый OTP или `ConfirmedAction` для resume не требуются. Она удаляет только owner pause и не снимает platform block, dispute или отсутствие оплаченного покрытия. `PUT` того же ресурса устанавливает паузу и требует `ConfirmedAction`; различие payload намеренное. UI отправляет resume только по явному действию пользователя.

## 9. Billing snapshots и подтверждённые финансовые факты

PlanVersion immutable после publish; FREE0EUR/1project/5seats/100000000storage/50 lifetime tasks per project; initial paid20EUR/month/5projects/50seats/5000000000storage/unlimited tasks. Single attachment20MB, avatar2MB вне tenant quota. Новые условия existing tenants — не ранее индивидуальной границы после mandatory inbox + notice30d; email retry не сдвигает effectiveAt. Catalog publish сам не меняет текущие лимиты.

Invoice states `DRAFT/OPEN/PARTIALLY_PAID/PAID/EXPIRED/VOID`; PAID не переоткрывается из-за refund. SubscriptionPeriod `GRANTED/REVOKED/SUPERSEDED`, активность вычисляется по времени и текущей allocation; старое independent coverage не отзывается оплатой дублирующего invoice. Invoice buyer/seller/lines/tax/FX/currency snapshots immutable. У partial wire создаются immutable invoice-payment matches, деньги остаются matched-but-unallocated: ни final allocation, ни coverage нет до проверенной полной суммы. `Invoice.matchedUnallocated` показывает ожидающую сумму, `remaining=max(total-allocated-matchedUnallocated,0)`; `PaymentFact.unallocated` включает matchedUnallocated. Например12/20 → matched12,allocated0,remaining8; после проверенных дополнительных8 final allocation20 создаётся один раз. Если доплаты до dueAt нет, возвращаются все12 matched-unallocated, не частичный subscription refund. Match не меняет сумму денежного факта и не создаёт второй приход; payment fact связан не более чем с одним invoice. Неоднозначное время остаётся на разборе, даже когда совпала сумма. Source reference unique; full payment invoice не создаётся повторным webhook/PSP+wire race.

Wire только EUR, default due7d, renewal lead7d, expected reconciliation24h от actual occurrence. Для EXACT это occurredAt; для DAY показывается диапазон target deadline [occurredNotBefore+24h,occurredBefore+24h), не выдуманный точный SLA timestamp; истечение целевого срока само не активирует/refund. Receipt запись — финансовый факт, не PAID. `confirmWireReceipt` принимает explicit confirmed=true и evidenceReference, без дополнительного OTP (D248); verified full timely amount даёт period от admin confirmedAt для первой/возобновлённой оплаты, early renewal — от current endsAt. First excess распределяет invoice sum и отдельный unallocated return, не дополнительный месяц. Late initial→return+replacement invoice без сдвига creationDeadline; late renewal допустимой живой компании→новый месяц от confirmedAt (D247). Closed/cancelled creation→return, кроме timely AUTO_CLOSED exception. Unmatched money stays MANUAL_REVIEW; outcome не угадывается. Отдельный PLATFORM-only `/admin/billing/unmatched-wire-receipts` сохраняет неподтверждённые/неидентифицированные приходы без tenant и без выдуманного payer. Record/list не создают PaymentFact/coverage; assignment требует verified payerRef и invoice, атомарно связывает исходный receipt с одной tenant PaymentFact, сохраняя global dedupe `(providerAccountId, bankReference)`. Assignment не подтверждает оплату; следующий confirm выполняет обычные checks. Raw account credentials не принимаются: providerAccountId — allowlisted configuration identifier. Для WIRE PaymentFact обязателен verified opaque `payerRef` (не raw банковские данные); для PSP он опционален, возврат ограничивается исходной provider payment identity. `POST /admin/billing/wire-receipts/{paymentId}/evidence-refinements` добавляет immutable FinancialEvidenceRefinement с digest/sourceFactId/verifiedBy/verifiedAt; actor и время верификации серверные. Confirm выбирает уже проверенный evidenceId этого же факта. Уточнение DAY→EXACT не создаёт второй денежный факт и не изменяет первоначальное evidence.

Checkout redirect/callback browser success не доказательство. Stripe выбран владельцем 03.11.2026 как первый PSP; сменяемый PaymentProvider port сохраняется. `ProviderInboxService.ObserveProviderWebhook` принимает exact raw bytes/signature только от mTLS allowlisted `SERVICE payment-adapter`, без caller tenant. Provisioned PSP verifier проверяет подпись/expiry и merchant/environment; private payload сохраняется зашифрованным до ACK. `RegisterProviderPayment` публикует локальную неизменяемую привязку из billing owner, а асинхронный `ProcessProviderWebhook` создаёт канонический normalized proof (event/payment identity, merchant, invoice, amount/currency, occurred/observedAt, evidence digest) и передаёт его через `PaymentSettlementService.ApplyVerifiedPayment`. [Реализованные RPC и границы включения](../../../billing-service/PROVIDER-INBOX.md); клиентское SUCCEEDED не является финансовым фактом. Реальный seller/merchant, live credentials, webhook signing key и разрешённые countries/methods/FX/document profiles подключает оператор позднее; отсутствие этих конфигураций запрещает live, а не требует повторно выбирать PSP. Fake и Stripe sandbox adapters реализуют тот же порт; sandbox readiness не выдаётся за live configuration.

Refund.kind имеет только `SUBSCRIPTION_FULL` и `UNALLOCATED_RETURN`; отдельный closed `reasonCode`: FULL — BILLING_ERROR/SERVICE_FAILURE/MANDATORY, RETURN — EXCESS/LATE_FIRST_PAYMENT/CLOSED_CREATION/INCOMPLETE_BANK_PAYMENT/DUPLICATE_PAYMENT. Free-text reason — пояснение, не новый kind и не permission. Refund `SUBSCRIPTION_FULL` возвращает весь allocated subscription payment; API не содержит amount для частичного subscription refund. `UNALLOCATED_RETURN` — отдельный возврат всего остатка по D237/D246 и не отзывает оплаченный период. State `REQUESTED/APPROVED/SUBMITTING/UNKNOWN/CONFIRMED/FAILED/REJECTED`; approve/submit не CONFIRMED. Confirm требует внешний verified settlement fact исходного payer/source и отдельную проверку суммы/deduplication; отправка поручения не равна зачислению. Full confirmed refund отзывает только соответствующее coverage и autopay; independent paid coverage пересчитывается. Request owner — не автоматически одобренный refund; D248 требует explicit confirmation без дополнительного OTP.

Dispute `OPEN/WON/LOST/WITHDRAWN/NEEDS_REVIEW`; конечные outcomes — `WON`, `WITHDRAWN_CONFIRMED`, `LOST_FULL_REFUND`, `LOST_PARTIAL_COVERAGE_REVOKED`. `NEEDS_REVIEW` допустим только до окончательного подтверждённого исхода; прежний command `PARTIAL_MANUAL_REVIEW` больше не принимается, его protobuf number/name reserved. При окончательном частичном chargeback записываются state=LOST, finalOutcome=LOST_PARTIAL_COVERAGE_REVOKED, resolvedAt и ссылка confirmedMoneyFactId на уже проверенный денежный факт этого payment. Отзывается только связанное с ним coverage; остаток его прежнего периода не сохраняется. Это регистрация внешнего факта, не заявка/команда на refund: дополнительный исходящий возврат, повторное списание и второй денежный факт запрещены. Старый/дублирующий payment без связанного текущего покрытия не отзывает независимый валидный period той же компании; effective access пересчитывается по всем независимым покрытиям и ограничениям. Если другого валидного покрытия нет, для платного доступа нужна новая полная подтверждённая оплата: PSP actual success либо WIRE confirmedAt запускает новый полный календарный месяц, без переноса остатка отозванного периода. WON/verified WITHDRAWN восстанавливает только оставшееся валидное покрытие; LOST_FULL_REFUND применяет уже подтверждённый полный возврат, также без второй выплаты. Generic CLOSED нет. Старое autopay consent отключено; возобновление требует нового явного согласия текущего owner. Retry того же исхода не меняет ledger/period повторно.

Банковские возвраты используют утверждённую `WIRE_RETURN_ES_V1`: решение и отправка выполняются в пределах **5 рабочих дат после получения полного комплекта необходимых сведений**, комиссия исходящего перевода за счёт Taska, без удержания из principal. Refund.sourceMethod производен от исходного payment; клиент не выбирает канал возврата/fee. Первый evidenceCompletedAt неизменяемо запускает один clock: decisionDueAt=sendDueAt. Время решения, reassignment, retry и повторная загрузка тех же evidence не дают новые 5 дней. После complete evidence сохраняются businessCalendarId, calendarVersion, slaPolicyVersion и закрытый RefundSlaSnapshot; до него дедлайн не выдумывается. Целевой срок не обещает межбанковское зачисление и не переводит отправленный/UNKNOWN перевод в CONFIRMED. Нарушение срока фиксируется как breach/escalation; оно не отменяет возврат и не запрещает позднее исполнение обязательства.

Календарь `WIRE_RETURN_ES_V1`: Europe/Madrid, исключить локальную дату evidenceCompletedAt, отсчитать следующие 5 Mon–Fri business dates за вычетом версионированных национальных и regional/local bank nonworking dates местонахождения продавца; сохранить исходное local wall time. При DST gap — ближайший следующий валидный instant, при overlap — later offset. Calendar version+digest фиксируются в snapshot. Реальный календарь продавца provisioned вместе с live merchant; именованная sandbox fixture никогда не подставляется в live. Бизнес-правило срока и комиссии уже принято и не ожидает отдельного согласования.

Owner plan-change FREE applies immediately if eligible; paid cheaper applies after new payment with new full month; upgrade next period. Opening invoice не меняет current rights. Cancel renewal сохраняет paid-through и не переключает FREE автоматически. Autopay consent отдельный от manual pay: Tenant.ownerVersion увеличивается только при transfer. Mandate фиксирует ownerId+ownerVersion+consentTermsVersion+consentChannel(WEB/PAT/OAUTH/MCP) и закрытый immutable ConsentSnapshot с terms digest, реальным actor/channel, requestId, timestamp и non-secret paymentMethod UUID. Эти атрибуты берутся из проверенного контекста, не принимаются как authority от клиента. Каждый automatic attempt сверяет актуальный ownerVersion и действующее согласие; consent старого владельца не переживает transfer, даже если его запись пришла позднее. Autopay owner-bound; transfer, full refund, pause/block/dispute останавливают будущие attempts, UNKNOWN уже отправленных — reconciliation, не двойное списание.

## 10. Confirmation, deletion и приватные файлы

Tenant delete: explicit boolean + exact confirmedName + отдельный purpose code. Account delete: отдельный code и глобальная проверка owner/last-admin memberships; checks повторяются после глобального account admission fence, включая race с concurrent promotion/transfer. В tenant DB `account_offboarding` guard закрывает новые memberships/ownership/admin assignments; команды берут user guards в стабильном UUID-порядке, затем tenant lock. Все leave/remove/demotion/suspend и account-deletion steps под тем же tenant lock считают выживших ACTIVE TENANT_ADMIN, исключая accounts с ADMISSION_CLOSED/REMOVING_MEMBERSHIPS/COMPLETED; count выполняется свежим READ COMMITTED statement после lock. Поэтому одновременные self-delete A/B или уход B после precheck A не оставляют компанию без администратора: конфликт закрывает одну операцию отказом без irreversible удаления, её fence снимается. Перед irreversible auth tombstone повторно проверяются все memberships; stale snapshot не считается подтверждением. `DELETE_TENANT`, `DELETE_ACCOUNT`, `CHANGE_EMAIL`, `ADMIN_LOGIN` непереставляемы; code binding включает account/tenant/version/generation, expired/replayed код не исполняет действие. Коды не доступны user integrations через обычное чтение уведомлений.

Exports/downloads — authenticated proxy, source/target ACL проверяется при fetch (включая Range). DTO downloadPath — путь gateway, не presigned URL. Удаление/смена роли/expiry между созданием и fetch запрещают выдачу. Financial documents owner-only либо admin target scope; exports не включают platform audit, tokens или billing private evidence. Upload presign допустим только bounded staging key + immutable pinned object version; confirm повторно авторизуется и server-side copy фиксирует final content до quota commit.

Retention/offboarding исполняются по принятой [версионированной политике ES_V1](../retention-policy.md), а не по ожидаемому будущему ответу владельца. При отсутствии применимой provisioned policy исполнение destructive command→503 POLICY_NOT_CONFIGURED до удаления данных; это runtime readiness guard, не открытый бизнес-вопрос. Доступ к финансовым документам после удаления выполняется через внутренний операторский CLI TAS-482: case, проверка личности/полномочий, whitelist документов, audit receipt и private evidence; удалённая web identity не восстанавливается, новый публичный REST endpoint не вводится. Перед началом offboarding tenant-service атомарно ставит lifecycle=DELETING и увеличивает deletionGeneration; gateway/authority прекращают новые admissions. Каждый resource-owner устанавливает собственный durable fence в транзакции с сериализацией по tenant; write transactions и install-fence берут тот же локальный lock. Уже admitted write либо commit до local fence и входит в cleanup, либо отклоняется после fence. Простая remote проверка перед commit не считается атомарным барьером. После установки локального fence старый mutation/upload confirm/export/job не создаёт ресурс; cleanup steps идемпотентны по (tenantId,deletionGeneration,service), final DELETED только после всех fence/cleanup acknowledgements. Company delete не удаляет глобальные профили участников. `DELETED` account display в ordinary API/export — «Удалённый пользователь», без старого avatar/email/name snapshots; financial/audit records сохраняются по утверждённой отдельной retention policy.

## 12. Совместимость, проверки и готовность конфигурации

Existing REST data routes не переименовываются этой схемой; их DTO остаются baseline, но обязательны target auth/tenant/ACL/flag rules из inventory. Новые additive endpoints зарегистрировать отдельно; generated stubs не редактировать вручную. Blueprint request/response message names и field numbers фиксируются в implementation; удалённые protobuf поля reserved, unknown enum=UNSPECIFIED отвергается, message absence не означает default allow. HTTP v1 изменения login/PAT security объявить явно в rollout, обновить UI/MCP/OAuth adapters совместно, revoke old generations перед открытием tenant data.

Проверки схем: `validate_contracts.py` валидирует OAS3.0.3, refs/paths/closed DTO/policies, unique operation IDs, соответствие REST↔RPC, 78 positive/negative schema examples, 7 temporal reference cases (DAY deadline overlap и запрет пустого интервала) и 14 billing/SLA reference scenarios (linked coverage, duplicate fact, new payment month, frozen deadline и DST) и source anchors inventory. Proto компилируется вместе с baseline common.proto через protoc4.33.5. Это статические проверки design artifacts, не tests реализации/security/E2E.

```sh
python3 docs/b2b/contracts/validate_contracts.py
protoc -I docs/b2b/contracts -I grpc-common-lib/src/main/proto -I "$PROTOBUF_INCLUDE" \
  --include_imports --descriptor_set_out=target/b2b-contracts.pb docs/b2b/contracts/b2b.proto
python3 scripts/harness.py docs-check
```

Implementation acceptance: cross-tenant URL/body/header/RPC/MCP mismatch, suspended/revoked owner rights, admin USER grant no bypass, empty admin scope no platform, refresh family isolation, MFA bypass attempts, request assertion replay/body mutation, quota concurrency+UNKNOWN recovery, duplicate payment/refund, independent restriction retention, current ACL at export download. Каждая mutation проверяет сохранность state при отказе; current code не объявлен проходящим эти сценарии.

### Unpaid creation errors (TAS-478 / A14)

For authorized working-content reads, `AWAITING_PAYMENT` returns `PAYMENT_PENDING` with reason `PENDING_FIRST_PAYMENT` (HTTP 409); `PROVISIONING` returns `INVALID_STATE` (409). This does not block owner metadata/status, payment or confirmed cancellation. The current tenant member RPC implements this guard; future gateway/project/workflow B2B adapters must preserve it. See [implemented lifecycle and financial-authority boundary](../../../tenant-service/CREATION-CLOSURE.md). Tenant DTO adds optional `creationClosureReason` and `creationClosedAt`; a valid timely full primary decision may clear the current AUTO_EXPIRED closure, while its receipt history remains immutable.

### Delivered entitlement foundation — TAS-319

[Entitlement snapshots](../../../billing-service/ENTITLEMENTS.md) implement `BillingService.GetEntitlement` and internal `EntitlementService.GetEntitlementSnapshot` with immutable tenant-scoped versions, period-bound validity and transactional outbox. Blueprint fields are preserved; `Entitlement.paid_through=11` adds the explicit exclusive coverage end required by TAS-319. Safe member reads use their own mandatory authority; financial-document owner/admin checks remain separate. Gateway activation, consumer projection and full capabilities are follow-up tasks, not implied by the backend transport.
