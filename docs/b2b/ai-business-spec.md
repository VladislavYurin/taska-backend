B01

B01. Граница продукта и запуск
------------------------------

*Решения: D01, D02, D03, D66, D67, D68, D69, D70, D71, D72, D120, D196, D208, D215, D216, D217, D218, D222*

Одна компания = один тенант, проекты внутри. Глобальный аккаунт может состоять в нескольких компаниях. Зарегистрированный пользователь сам создаёт компанию и выбирает FREE либо платный тариф, становится владельцем и TENANT\_ADMIN. Самостоятельное создание компаний — базовая возможность без отдельного выключателя; платные права требуют подтверждённой оплаты.

**D208 — компания, созданная сразу на платном тарифе, ожидает первую подтверждённую оплату. Владельцу доступны оплата, её статус и подтверждённая отмена создания по D217; проекты, приглашения и прочие рабочие функции недоступны. FREE автоматически не включается и FREE-возможность не расходуется. Оплаченные права включаются после подтверждения по правилам PSP/банка B06/B09; административное исключение — B02.**

D215 — неоплаченное создание автоматически закрывается через настраиваемый срок, default 30 суток от создания компании (UTC). Параметр общий, управляется GLOBAL\_ADMIN. Deadline хранится для конкретного создания; retry и новый счёт его не продлевают. Правило касается только компании, созданной сразу на paid и ещё не имевшей первой подтверждённой оплаты; работающая FREE и ранее оплаченная компания с просроченным продлением не подпадают. Закрытие не включает FREE, не расходует FREE-возможность, не затрагивает аккаунт/другие компании. Сроки счетов отдельны, финансовые факты и история сохраняются; физический purge/retention — O09. Своевременная полная оплата — D216, ранняя отмена — D217; обычное возобновление запрещено D218; урегулирование денег — O04.

D216 — полная оплата до срока счёта и deadline создания активирует ту же компанию даже после автозакрытия D215, если подтверждение получено позднее. Своевременность проверяется по данным PSP/выписке, не по времени доставки сообщения; период — B06/B09, повтор не создаёт второй период. Исключение только для автозакрытия: явная отмена D217, удаление владельцем и независимые блокировки им не отменяются. Частичная/фактически поздняя оплата не считается своевременной полной; урегулирование — O04.

D217 — владелец может подтвердить отмену неоплаченного создания до истечения срока, не ожидая автозакрытия. Это явная отмена владельцем, отличная от закрытия по D215; позднее подтверждение платежа не восстанавливает такую компанию автоматически по D216. Финансовые записи и уже поступившие деньги остаются для сверки. FREE не включается и FREE-возможность не расходуется. Команда относится только к незавершённому неоплаченному созданию, а не к прекращению уже работающей оплаченной компании; обычное возобновление после закрытия запрещено D218.

D218 — неоплаченное создание, автоматически закрытое по D215 или отменённое владельцем по D217, обычным способом не возобновляется: владелец создаёт новую компанию. Единственное согласованное исключение — D216: своевременная полная оплата при позднем подтверждении активирует ту же автоматически закрытую компанию, но не отменённую владельцем. Закрытое создание и его финансовые записи сохраняются для сверки; новое создание не продолжает его lifecycle. Условия урегулирования денег — O04, сроки хранения — O09. Общие административные полномочия — B02.

Первый платный запуск международный, для организаций, предпринимателей и частных лиц. Продавец планируется в Испании, регистрация ещё не подтверждена. Фактическая коммерческая готовность остаётся условием TAS-271.

Для B2B выполняется чистый старт: старые тестовые проекты, обычные аккаунты и зависимые тестовые данные удаляются по подготовленному runbook. Legacy tenant/backfill и перенос старых объектов не нужны. Сохраняются GLOBAL\_ADMIN и служебные конфигурации; первый администратор создаётся существующим initializer при отсутствии. Демонстрационный USER создаётся только при явно включённом тестовом режиме, default=false.

Логотипа компании нет. D222 — перенос проектов между компаниями отложен для всех ролей, включая GLOBAL\_ADMIN, до отдельного этапа и не входит в первую B2B-версию. Ограниченная роль технического саппорта — отдельный будущий этап. Это целевые требования, а не утверждение о работающем develop/стенде.

B02

B02. Роли, владение и администрирование
---------------------------------------

*Решения: D09, D10, D22, D24, D25, D26, D28, D29, D31, D32, D51, D52, D59, D175, D197, D198, D199, D200, D201*

GLOBAL\_ADMIN имеет полный административный доступ ко всем компаниям/проектам/содержимому без членства и разрешения владельца, включая обход тарифных квот, бизнес-флагов, финансового READ\_ONLY, паузы и блокировки. Прежняя модель обязательной ограниченной support-сессии отменена. Запись сверх лимита увеличивает реальное использование, не скрывает превышение. Изменение данных само не снимает причину блокировки и не делает платёж успешным. Достоверная аутентификация, целостность, идемпотентность и внутренний аудит реального actor сохраняются. Владелец и tenant-роли не видят платформенный журнал GLOBAL\_ADMIN; это не разрешает фальсифицировать обычную историю задач.

TENANT\_ADMIN имеет права project ADMIN во всех проектах своей компании, в том числе закрытых и без явного membership. Только TENANT\_ADMIN создаёт проекты и приглашает новых людей в компанию; любой активный TENANT\_ADMIN назначает/снимает такую роль с учётом защиты владельца и последнего активного администратора. Project ADMIN и TENANT\_ADMIN добавляют в проект уже активных участников компании.

Среди обычных пользователей только владелец управляет подпиской, оплатой, отменой продления, финансовыми документами/заявками и удаляет компанию. Административное исключение GLOBAL\_ADMIN имеет приоритет.

Передача владения: только платная компания с действующим оплаченным периодом, включённый флаг; получатель — любой активный участник той же компании, согласие получателя не требуется. Новый владелец становится TENANT\_ADMIN, прежний остаётся TENANT\_ADMIN без финансовых прав. Старое согласие на автосписания отключается; новый владелец выбирает свой способ и даёт новое согласие. FREE передавать нельзя. Другие обычные бизнес-ограничения учитываются; их сочетание с передачей отмечено в открытых вопросах.

B03

B03. Членство, справочник и приглашения
---------------------------------------

*Решения: D07, D11, D12, D33, D53, D54, D55, D56, D57, D58, D60, D61, D62, D63, D64, D65, D132, D171, D172, D173*

Лимит мест считает уникальных участников компании, включая владельца, плюс действующие резервы приглашений. Один человек в нескольких проектах занимает одно место. SUSPENDED продолжает занимать место, освобождение — при удалении membership/выходе.

Приглашение сразу резервирует место; принятие однократно преобразует резерв в membership. Отзыв/истечение освобождает резерв; повтор/доставка не расходуют второе место. TTL=7 суток, настраивается; старый expiresAt не меняется от настройки. TENANT\_ADMIN может заранее выбрать проекты и роли. При принятии выдаются доступные проекты, пропуски явно сообщаются; компания принимается даже если ни один проект недоступен. Утрата отправителем TENANT\_ADMIN/выход отменяет его непринятые приглашения.

Финансовый READ\_ONLY из-за неоплаты/квот допускает принятие ранее выданного действующего приглашения без второго места. Пауза владельцем и блокировка платформой запрещают принятие; TTL продолжает идти, истёкшее после снятия запрета не восстанавливается.

Обычный участник видит имя, аватар и email всех участников своей компании, без открытия их проектов. Самостоятельный выход разрешён, включая финансовый READ\_ONLY, кроме владельца/последнего активного TENANT\_ADMIN до передачи обязанностей.

Удаление/выход и SUSPENDED снимают назначения исполнителем с сохранением задач/истории. Старые назначения и проектные доступы автоматически не возвращаются при rejoin или reactivation. SUSPENDED TENANT\_ADMIN включается как MEMBER; роль назначают заново. Retry очистки не снимает нового исполнителя.

B04

B04. Каталог, тарифы и FREE-возможность
---------------------------------------

*Решения: D04, D05, D06, D08, D15, D17, D20, D21, D38, D84, D133, D134, D135, D136, D207*

Версионированный каталог БД содержит описание, цену, валюту, лимиты и возможности; условия счетов и оплаченных периодов сохраняются snapshot. Цена фиксированная за компанию, не за фактические места.

Первый запуск: FREE — 0 EUR, 1 проект, 5 участников; платный — 20 EUR в календарный месяц с применимыми налогами, 5 проектов, 50 участников. Более крупные уровни добавляются позднее каталогом. Платного trial нет.

Одна собственная FREE-возможность за всю жизнь аккаунта; платных компаний может быть несколько, участие в чужих компаниях этим не ограничивается. FREE→paid→FREE той же компании разрешён. Впервые созданная платной компания может перейти на FREE, если у владельца возможность не использована; переход закрепляет её за компанией. После платной передачи проверяется возможность нового владельца: если связана с другой компанией, FREE запрещён; если не использована — расходуется на эту; прежнему владельцу право не возвращается.

Удаление компании/аккаунта не восстанавливает использованную возможность. Повторная регистрация с тем же подтверждённым email бессрочно не даёт новую FREE-компанию. Это не запрет регистрации/платной работы/чужих memberships. Минимальный учёт и политика хранения требуют оформления; fingerprinting и поиск личности по разным email не утверждены.

B05

B05. Квоты проектов, задач и хранения
-------------------------------------

*Решения: D27, D30, D137, D138, D139, D140, D141, D142, D166, D184, D185, D186, D187, D188, D189, D190, D191, D192, D193, D194, D195*

Проекты: архивный проект занимает место; только безвозвратное удаление освобождает проектную квоту. Удаление проекта — после подтверждения, без корзины, с однократной очисткой квот.

Задачи FREE: maxTasksPerProject=50, настраиваемый lifetime-лимит успешных созданий каждого проекта. Все типы занимают по одному месту; смена типа не меняет usage. Завершение и удаление задачи место не возвращают. Учитываются создания и во время paid, месячного сброса нет. Retry одного создания не расходует повторно, неуспешная операция не теряет место навсегда.

Ровно 50: запрет новых задач, редактирование/комментарии/переходы по правам продолжаются при отсутствии иных ограничений. Больше 50 после paid→FREE: компания READ\_ONLY, задачи сохранены. На платном тарифе task limit отсутствует, исторический счётчик ведётся. Новый проект после безвозвратного удаления старого имеет новый счётчик и собственные 50; архивирование/переименование не сбрасывает usage.

Хранение: FREE 100 000 000 байт, paid 5 000 000 000 байт; один attachment максимум 20 000 000 байт. Общий аватар аккаунта максимум 2 000 000 байт и НЕ входит ни в одну tenant quota. Размеры настраиваются в каталоге/типизированных параметрах, int64 для storage. Учитываются подтверждённые байты и активные reservations.

Переход на меньшие лимиты разрешён с сохранением данных; превышение приводит к READ\_ONLY, а не автоматическому удалению. При storage READ\_ONLY не разрешено удалять отдельные вложения ради освобождения места; допустимо удалить проект либо сменить тариф. Удалённые задачи не уменьшают lifetime task usage. GLOBAL\_ADMIN может превысить квоты, с честным учётом и сохранением ограничений для участников.

B06

B06. Периоды подписки, изменение условий и тарифов
--------------------------------------------------

*Решения: D13, D14, D16, D18, D19, D23, D39, D40, D44, D47, D48, D73, D147, D157, D158, D191, D192, D209, D210, D211, D212, D213, D214, D235*

Расчёты в UTC, локальное время только отображается. Календарный месяц с индивидуальным anchor: для PSP первая успешная оплата, при unpaid gap новая успешная оплата даёт полный месяц и новый anchor, без долга за неоплаченный READ\_ONLY. День 31 ограничивается последним днём короткого месяца и восстанавливается в следующем подходящем (31 января→28/29 февраля→31 марта).

Для банковской первой оплаты/возобновления истёкшей подписки начало полного месяца — подтверждение GLOBAL\_ADMIN (D235); факт поступления по выписке хранится отдельно. Заблаговременно подтверждённое продление действующего периода без смены тарифа начинается с его конца, сохраняя anchor.

По окончании paid-through без продления сразу READ\_ONLY, без grace. Повышение платного тарифа — только со следующего периода. D209–D211: добровольный paid→FREE применяется сразу после выбора владельцем, если допустима FREE-возможность. Переход на более дешёвый платный тариф применяется сразу после подтверждения отдельной оплаты нового тарифа, с новым полным месячным периодом и новой датой окончания, без прибавления месяца к прежнему сроку. PSP — успешная оплата; банковский перевод — подтверждение GLOBAL\_ADMIN (D235). Автоматического возврата за остаток старого периода нет, исторические платежи и invoice snapshots не переписываются. Новые лимиты/capabilities действуют с фактического перехода; превышение квот нового тарифа даёт READ\_ONLY с сохранением данных, а при соблюдении квот работа продолжается. Переход на FREE сохраняет правила единственной FREE-возможности. Возврат с FREE на прежний платный тариф в ранее оплаченном интервале требует новой оплаты и нового месяца по D212.

D211 — пока отдельная оплата более дешёвого платного тарифа не подтверждена, сохраняются прежний тариф, его права и лимиты до конца уже оплаченного срока. Открытие счёта, ожидание, ошибка оплаты или повтор запроса сами тариф не меняют и не продлевают прежний срок. Если он истёк до подтверждения новой оплаты, компания переходит в READ\_ONLY по обычному правилу неоплаты. Подтверждение нового платежа немедленно включает новый тариф и новый полный месяц по D210; повторное подтверждение не создаёт второго периода. Иные причины ограничений (пауза, блокировка, права) продолжают действовать. Таким образом, «немедленно» для paid→paid означает после подтверждения оплаты, а для paid→FREE — после выбора владельцем.

D212 — после перехода с платного тарифа на FREE возврат на тот же платный тариф требует новой оплаты и нового полного месячного периода, даже если прежняя оплаченная дата окончания ещё не наступила. Остаток старого периода не восстанавливается и не прибавляется к новому. До подтверждения новой оплаты остаётся FREE с его лимитами и действующими причинами READ\_ONLY; старый платёж не открывает прежние платные права. Начало нового периода — подтверждённая оплата PSP либо подтверждение банковского поступления GLOBAL\_ADMIN (D235) по правилам B06/B09. Исторические платежи/счета сохраняются; повтор подтверждения одного платежа не создаёт второго периода.

D213 — отмена продления не прекращает уже оплаченный доступ досрочно. Если новый период не оплачен и владелец не выполнил переход на другой тариф, по окончании оплаченного срока компания переходит в READ\_ONLY. Автоматического перехода на FREE нет: владелец выбирает его отдельно, с ранее утверждёнными проверками FREE-возможности и лимитов. Отмена продления и истечение срока сами не расходуют FREE-возможность. Отключение автосписаний остаётся отдельным действием и допускает ручное продление.

Изменение базовой цены/лимитов существующей платной подписки — с первой индивидуальной границы после срока предупреждения, default 30 полных суток (настройка). Обязательные email + inbox владельцу. Отсчёт от созданного обязательного inbox; не от прочтения. Неуспешный email повторяется, не сдвигая согласованную дату. Оплаченный период и выданный invoice не переписываются.

D214 — новая компания на FREE получает лимиты выбранной опубликованной версии тарифа сразу. Для уже существующих FREE-компаний новая версия лимитов применяется по истечении настраиваемого срока предупреждения (по умолчанию 30 суток), без дополнительной месячной границы. Начало отсчёта — создание обязательного уведомления владельцу внутри Taska; email также обязателен, а его сбой не сдвигает дату применения и обрабатывается повторными отправками по B13. До effectiveAt сохраняются прежние лимиты; с effectiveAt действуют новые. Если использование выше новых лимитов, включается READ\_ONLY с сохранением данных и согласованными способами выхода из превышения; иначе работа продолжается по обычным правам. Публикация версии каталога сама по себе не применяет новые лимиты досрочно к существующим компаниям. Накопительные счётчики задач сменой версии не обнуляются.

B07. READ\_ONLY, паузы и блокировки
-----------------------------------

**D244 — решение владельца от 02.11.2026.** Обычный владелец может передать владение или удалить компанию при своей owner pause. При platform block либо открытом банковском dispute оба действия запрещены обычному владельцу. Независимые условия сохраняются: передача только при действующем платном покрытии и включённом флаге; удаление с согласованными подтверждениями. GLOBAL\_ADMIN сохраняет административное исключение B02. O12 закрыт.

*Решения: D16, D19, D23, D57, D75, D76, D81, D82, D93, D94, D129, D130, D131, D144, D145, D146, D148, D149, D170, D171, D172, D173, D174, D199, D200, D201*

Независимые причины ограничений сочетаются; оплата не снимает platform block/owner pause. GLOBAL\_ADMIN имеет оговорённый полный доступ. Для участников при неоплате/over-quota сохраняются чтение и явные действия по восстановлению: TENANT\_ADMIN удаляет участников, отзывает приглашения, удаляет проекты; владелец оплачивает/меняет тариф, подаёт и отслеживает финансовые заявки. Самостоятельный выход обычного участника разрешён; действующее старое приглашение можно принять. Владелец может удалить компанию с двойным подтверждением и кодом. Отдельные вложения при storage READ\_ONLY удалять нельзя.

Владелец ставит компанию на паузу; блокировку платформы снимает только GLOBAL\_ADMIN. Один общий флаг чтения при owner pause/platform block имеет default=true; при false доступ к проектному содержимому закрыт для участников. Управление состоянием/разрешённые финансовые обращения не следует скрывать как проектное содержимое.

Уже оплаченный срок при паузе и platform block продолжает идти без автоматического продления/заморозки. Новые автосписания будущих периодов остановлены. Возобновление после expiry само не списывает деньги: владелец подтверждает оплату нового месяца. До expiry используется остаток срока. Ошибочные блокировки/проблемы услуги и возможная компенсация рассматриваются отдельно.

Подтверждённый открытый банковский спор по оплате текущего покрытия → временный READ\_ONLY и остановка новых автосписаний. Снятие причины требует подтверждённого исхода и проверки актуального покрытия; generic CLOSED не означает PAID. Оплата старого/дублирующего счёта не отменяет независимое валидное покрытие. Подтверждённые исходы спора определены B10/D230–D234; оставшиеся процедуры ручного разбора — O04.

B09

B09. PSP, банковские переводы и автосписания
--------------------------------------------

**D247 — решение владельца от 02.11.2026.** Фактически поздняя банковская оплата продления по счёту с истёкшим сроком, если компания не удалена и не заблокирована, после ручной сверки GLOBAL\_ADMIN засчитывается в новый полный месячный период с момента подтверждения. Не взыскивать пропущенные месяцы и не прибавлять новый месяц к старой истёкшей дате. Это правило продления; первая поздняя оплата незавершённого создания следует D238. Независимые ограничения не снимаются и повтор не создаёт второй период.

**D246 — решение владельца от 02.11.2026.** Частичная банковская оплата ожидает доплаты до срока счёта. Если к этому сроку полной оплаты нет, всё нераспределённое поступление направляется на возврат. Деньги закрытого или явно отменённого создания компании возвращаются без запуска компании; исключение D216 для своевременной полной оплаты автоматически закрытого создания сохраняется. Возврат фиксируется отдельной операцией; решение/отправка и подтверждённый возврат различаются.

*Решения: D49, D51, D88, D89, D130, D131, D145, D149, D150, D151, D152, D153, D154, D155, D156, D157, D158, D159, D160, D161, D162, D163, D164, D231, D235, D236, D237, D238, D239*

Первый платный запуск включает PSP и прямой банковский перевод. PSP сменяемый, hosted checkout, проверенные callbacks/inbox/reconciliation; успешная страница клиента не подтверждает оплату.

Автосписание требует явного согласия текущего владельца, настроенного метода, включённых PSP/autopay флагов и допустимого состояния. Первая ручная оплата не является согласием. Отмена согласия/пауза/платформенная блокировка/спор о текущем покрытии останавливают новые автоматические попытки; уже принятые сверяются, без двойной оплаты. После передачи владельца или полного возврата старый autopay отключён. После разрешения банковского спора старое согласие не восстанавливается: для возобновления требуется новое явное согласие текущего владельца по D231/B10.

Прямые переводы только EUR; USD доступен через PSP при готовности. На первом этапе только GLOBAL\_ADMIN подтверждает приход по выписке через аудируемое действие, автоматический импорт позже. Клиентский скриншот не PAID. Сумма счёта должна поступить полностью: частичные поступления суммируются, владелец видит остаток; комиссии перевода несёт покупатель. Независимое текущее покрытие не отзывается из-за частичной оплаты следующего периода.

Срок оплаты банковского счёта default 7 суток, настраиваемый; поздний реальный приход сохраняется и идёт на ручной разбор без автоматической активации. Если вся сумма пришла до срока, а GLOBAL\_ADMIN подтвердил позже, оплата своевременна и доплата за задержку не нужна.

Банковский календарь — B06. Счёт и напоминание на продление готовятся default за 7 суток до конца периода; lead time отдельно от срока оплаты. Обязательные email + inbox текущему владельцу, независимо от обычных notification opt-out. Повтор scheduler не создаёт второй счёт/напоминание.

Любые partial/over/unmatched/late поступления сохраняются в ledger; PSP+wire не закрывают один invoice дважды и не создают двойное покрытие. При своевременной первой переплате доступ предоставляется по D236, без ожидания разбора излишка. Излишек возвращается по D237; поздняя первая оплата открытого создания — D238. Процедуры возврата и остальные неурегулированные поступления — O04.

D236 — при первой банковской оплате по действующему счёту своевременное поступление суммы больше суммы счёта после подтверждения GLOBAL\_ADMIN считается полной оплатой счёта. Первый полный месячный период начинается с подтверждения по B06, не ожидая решения по излишку. Например: счёт 20 EUR, вовремя поступило 25 EUR; 20 EUR покрывают счёт, 5 EUR учитываются отдельно для ручного разбора, а в финансовом журнале сохраняется весь приход 25 EUR и его распределение без потери денег. Переплата и повтор подтверждения не создают дополнительного оплаченного периода или повторного финансового эффекта. Сохраняются действующие правила состояния компании и независимые ограничения B01/B07; D236 не отменяет явную отмену создания или блокировку. Излишек возвращается исходному плательщику по D237; процедура возврата остаётся O04.

D237 — нераспределённый излишек своевременной первой банковской оплаты возвращается исходному плательщику после проверки GLOBAL\_ADMIN. В примере D236 из прихода 25 EUR счёт покрыт 20 EUR, весь излишек 5 EUR направляется на возврат; аванс на будущие счета из него не создаётся. Оплаченные 20 EUR, текущий месячный период и его даты сохраняются. Возврат излишка сам не переводит компанию в READ\_ONLY, не снимает оплаченные права и не отключает автосписания; независимые ограничения продолжают действовать. Исходный приход, сумма покрытия счёта и возврат излишка учитываются раздельно со связью между ними. Решение/отправка перевода и подтверждённый возврат денег различаются; повтор не создаёт второй возврат или повторный финансовый эффект. Это возврат всего нераспределённого остатка, отдельный от исключённого D228 частичного возврата платы за подписку. Сроки, комиссии и процедура подтверждения банковского возврата остаются O04.

D238 — если полная первая банковская оплата фактически поступила после истечения счёта, а компания ещё ожидает первую оплату и её создание не закрыто, GLOBAL\_ADMIN после сверки оформляет возврат этого поступления исходному плательщику и выдачу нового счёта с актуальными условиями. Старый счёт не возобновляется, его условия и история не переписываются. Позднее поступление не активирует подписку и не засчитывается в оплату нового счёта: для активации нужна отдельная подтверждённая оплата нового счёта по обычным правилам. Новый счёт относится к той же ожидающей компании; deadline её создания по D215 не продлевается, FREE не включается и FREE-возможность не расходуется. Исходный приход, старый и новый счета, возврат и новая оплата сохраняются раздельно и связно. Решение/отправка возврата не равны подтверждённому возврату денег. Повтор обработки того же поступления не создаёт второй возврат, новый счёт или оплаченный период. Возврат старого позднего поступления не отменяет независимую новую подтверждённую оплату. D238 не меняет правило своевременной полной оплаты, подтверждённой позже (B09/D216): учитывается время фактического поступления, а не подтверждения GLOBAL\_ADMIN. Сроки/комиссии/доказательство банковского возврата остаются O04; исходы для уже закрытого или отменённого создания здесь не определяются.

D239 — показываемый пользователю целевой срок ручной сверки банковской оплаты настраивается; значение по умолчанию — 24 календарных часа с момента фактического поступления денег, включая выходные. Расчёт длительности ведётся в UTC без переноса на рабочий день. Начало отсчёта определяется банковским фактом, а не открытием счёта, заявлением пользователя, временем получения выписки или нажатием подтверждения GLOBAL\_ADMIN. Повтор обработки того же поступления не перезапускает отсчёт. Целевой срок сверки отличается от срока оплаты счёта, deadline создания компании и оплаченного месяца. Истечение 24 часов само не подтверждает оплату, не включает платные права и не запускает возврат; действуют проверенные финансовые факты и правила D235–D238. Первый банковский оплаченный месяц начинается после подтверждения по B06. Frontend получает настроенную длительность и показывает её как целевой срок ручной сверки. Это общая числовая настройка B11, а не отдельный boolean-флаг или tenant override. Сроки возврата/разрешения финансовых случаев и точность доступных банковских дат остаются O04.

B10

B10. Возвраты и финансовые споры
--------------------------------

*Решения: D74, D75, D76, D77, D78, D79, D80, D148, D149, D228, D230, D231, D232, D233, D234, D235, D237, D238*

Владелец подаёт запрос возврата в Taska, GLOBAL\_ADMIN рассматривает и оформляет. Заявка, одобрение и подтверждённый возврат — разные состояния. Заявки доступны владельцу и при финансовом READ\_ONLY.

Добровольный возврат «передумал» не предлагается. Рассматриваются ошибки списания, проблемы услуги и обязательные возвраты. Повторная оплата/период/смена владельца не очищает финансовую историю; GLOBAL\_ADMIN видит повторные обращения, но обязательные права не отменяются произвольным лимитом.

D228 — продуктовые частичные возвраты оплаты подписки в первой версии исключены для всех ролей, включая GLOBAL\_ADMIN. В UI/API/MCP и административных инструментах нет выбора произвольной части стоимости подписки для возврата; роль и scopes не добавляют отсутствующую функцию. Согласованные полные возвраты сохраняются. Внешние частичные финансовые факты фиксируются и сверяются, не выдаются за полный возврат; исходы споров — D230–D234, ручная сверка и урегулирование — O04.

Подтверждённый полный возврат платежа текущего покрытия снимает соответствующие оплаченные права, оставляет данные и переводит компанию в финансовый READ\_ONLY, отключает autopay. Возврат дублирующего/старого платежа не уничтожает независимое валидное покрытие. Возобновление autopay требует нового явного согласия.

Для банковских возвратов нужен подтверждённый финансовый факт; политику не заменять выдуманным PSP success. Исход спора в пользу Taska — D230; возобновление autopay — D231, окончательный проигрыш с полным возвратом — D232; отозванный и окончательно закрытый спор с сохранением оплаты — D233; частичный внешний chargeback — D234. Двойной refund+chargeback одного финансового факта исключается.

D230 — после подтверждённого PSP завершения банковского спора в пользу Taska автоматически снимается ограничение доступа, вызванное этим спором. Если соответствующий оплаченный период ещё действует и других ограничений нет, компания получает оставшийся ранее оплаченный доступ по прежним правам участников. Дата окончания не переносится, новый оплаченный период не создаётся. Истёкший период не восстанавливается. Независимые причины ограничения (квоты, пауза владельцем, блокировка платформой, другой открытый спор) сохраняются; результат пересчитывается по актуальному состоянию компании и покрытия. Повтор подтверждения не продлевает доступ и не создаёт новое покрытие. D230 определяет восстановление доступа; возобновление автосписаний требует нового согласия по D231.

D231 — если до банковского спора автосписания были включены, после разрешения спора и снятия ограничений их можно возобновить только после нового явного согласия текущего владельца. Старое согласие автоматически не восстанавливается. Закрытие спора и возврат оплаченного доступа по D230 сами по себе не включают autopay. Владелец заново подтверждает автоматическую оплату; сохраняются условия B09: настроенный способ оплаты, готовность PSP, включённые флаги и состояние, допускающее автосписание. Получение согласия не подтверждает оплату, не создаёт оплаченный период и не меняет его даты. Повтор обработки результата спора не заменяет согласия и не возобновляет автосписания по старому разрешению.

D232 — если спор окончательно проигран Taska и PSP подтвердил полный возврат платежа, обеспечивающего текущий оплаченный период, применяются правила подтверждённого полного возврата B10. Соответствующие платные права снимаются, данные сохраняются, компания переходит в финансовый READ\_ONLY с согласованными исключениями B07, autopay остаётся выключенным. Независимое действующее покрытие не отзывается из-за возврата другого платежа; ограничения пересчитываются по актуальным финансовым фактам. Подтверждённый возврат PSP не запускает дополнительный возврат денег. Повтор результата идемпотентен, не создаёт повторного возмещения и не отменяет новую независимую оплату. Возобновление autopay — только по новому согласию владельца по D231.

D233 — если клиент отозвал банковский спор, а PSP подтвердил его окончательное закрытие и сохранение оплаты у Taska, доступ восстанавливается автоматически по правилам D230. Возвращается только остаток действующего оплаченного периода по прежним правам участников; дата окончания не переносится, истёкшее покрытие и другие ограничения не отменяются. Дополнительная проверка GLOBAL\_ADMIN для этого подтверждённого исхода не требуется. Само заявление клиента об отзыве без окончательного подтверждения PSP не считается разрешением спора. Autopay остаётся выключенным до нового согласия текущего владельца по D231. Повтор подтверждения не продлевает период, не создаёт новое покрытие и не включает старое согласие.

D234 — если спор окончательно закрыт и PSP подтвердил возврат банком только части оплаты за текущий период, случай передаётся GLOBAL\_ADMIN на ручной разбор. До решения компания остаётся в финансовом READ\_ONLY с согласованными исключениями B07; автоматического восстановления оплаченного доступа нет. В финансовом журнале сохраняется фактическая частичная сумма, её связь с платежом/спором и история; она не превращается в полный возврат. Данные компании сохраняются, autopay остаётся выключенным; его последующее возобновление требует D231. Повтор подтверждения не создаёт второй финансовый эффект или повторный случай. Это внешний финансовый факт, а не функция частичного возврата оплаты подписки. Ручной разбор выполняет только GLOBAL\_ADMIN по D235; сроки и допустимые решения согласуются в O04.

D235 — в первой версии только GLOBAL\_ADMIN вручную сверяет и подтверждает банковские оплаты, разбирает финансовые случаи, принимает административные решения по заявкам и оформляет согласованные полные возвраты оплаты подписки и возврат переплаты по D237. Отдельная финансовая роль в первый релиз не входит. Обычный владелец сохраняет оплату, управление подпиской, подачу и отслеживание своих финансовых заявок; это не даёт ему, TENANT\_ADMIN или MEMBER права подтверждать поступление денег, одобрять или исполнять возврат от имени Taska без роли GLOBAL\_ADMIN. Для административных PAT/OAuth/MCP сохраняются D223–D227: текущая роль, явно выданное разрешение на операцию, уровень изменений и соответствующая область. Финансовые действия не становятся только веб-операциями. Проверенные банковские/PSP-факты, внутренний аудит и отсутствие повторного финансового эффекта обязательны; роль не подменяет подтверждение поступления или возврата. Сроки и допустимые решения ручного урегулирования остаются O04.

D237: возврат всего нераспределённого банковского излишка исходному плательщику после проверки GLOBAL\_ADMIN разрешён по B09. Он сохраняет оплату подписки и оплаченный период. D228 исключает частичный возврат стоимости подписки; правило полного возврата с отзывом оплаченных прав к возврату излишка не применяется.

D238/B09: полная первая банковская оплата, пришедшая после срока счёта при ещё открытом ожидании первой оплаты, возвращается исходному плательщику; выдаётся новый счёт на актуальных условиях. Нужна новая подтверждённая оплата. Возврат позднего поступления и его подтверждение учитываются отдельно, не отзывают независимое новое покрытие; повторы не дублируют возврат. Своевременный приход с поздним подтверждением остаётся своевременным.

B12. Каналы, аккаунты и контракт доступности
--------------------------------------------

**D248 — решение владельца от 02.11.2026.** Для передачи владения, ручного подтверждения банковской оплаты и возврата в первой версии достаточно действующей сессии с нужными правами и явного подтверждения действия. Дополнительные одноразовые коды для этих трёх действий не вводятся. Обязательный email-код веб-входа GLOBAL\_ADMIN и отдельные коды удаления компании/аккаунта сохраняются. **D245 — решение владельца от 02.11.2026.** Первого GLOBAL\_ADMIN подключает оператор по эксплуатационной процедуре. Если подтверждённая почта GLOBAL\_ADMIN недоступна, её заменяет только другой действующий GLOBAL\_ADMIN либо оператор по процедуре восстановления. Самостоятельный обход второго фактора не вводится. Процедура должна подтверждать полномочия инициатора/целевого аккаунта, фиксировать внутренний аудит и завершаться подтверждением новой почты; при восстановлении отзываются сессии, которые нельзя считать доверенными. Само наличие первого фактора не разрешает сменить адрес второго фактора.

**D243 — решение владельца от 02.11.2026.** Обязательный двухфакторный вход в первой версии требуется только GLOBAL\_ADMIN. Для владельцев компаний и TENANT\_ADMIN обязательная 2FA не вводится. Подтверждения удаления компании/аккаунта остаются отдельными согласованными действиями и не отменяются этим решением.

**D242 — решение владельца от 02.11.2026.** Второй фактор веб-входа GLOBAL\_ADMIN — одноразовый код на подтверждённую почту аккаунта. До успешной проверки кода полноценная административная веб-сессия не выдаётся. Код связан с попыткой входа и аккаунтом, ограничен по времени/попыткам и используется один раз; значения этих технических лимитов документируются в контракте. TOTP и Telegram как второй фактор входа этой редакцией не вводятся.

*Решения: D90, D103, D104, D114, D115, D116, D117, D121, D122, D176, D179, D180, D219, D220, D221, D223, D224, D225, D226, D227, D228, D237, D240*

Web по обычной сессии не является PAT. Выключение PAT запрещает выпуск новых токенов и новые запросы с ними, но оставляет безопасный просмотр метаданных/отзыв. Выключение MCP запрещает новые операции даже по старой сессии; веб работает по своим правилам.

D219 — персональный API-токен обычного пользователя, включая владельца и администратора компании, привязан к одной компании, выбранной при выпуске. Для другой компании выпускается отдельный токен. Членство пользователя в нескольких компаниях и переключение компании в веб-интерфейсе не расширяют область токена. Запрос по этому токену не может выбрать другой tenant через URL/header/body, идентификатор проекта или задачи. При каждом запросе проверяются актуальные права пользователя, scopes, тариф, флаги и состояние выбранной компании. MCP с таким PAT сохраняет ту же привязку. D220 — OAuth-разрешение обычного пользователя при подключении AI-клиента выдаётся на одну выбранную компанию; для другой компании требуется отдельное разрешение. Компания явно выбирается при согласии в браузере и показывается на экране согласия и в списке подключений. Выданные по этому разрешению токены, их обновление и MCP-сессии сохраняют эту область доступа. Смена компании в вебе или передача другого tenant/project/task ID не переключают существующее разрешение. Актуальные права, scopes, тариф и бизнес-флаги целевой компании проверяются для каждой операции. Изменение глобального аккаунта ограничено D221, административный канал — D223; компании — D224, уровни доступа — D225; глобальные аккаунты — D226, выдача/расширение разрешений — D227; частичный возврат подписки исключён D228.

D221 — для обычного пользовательского доступа изменение глобального профиля (включая имя и аватар), смена пароля, самостоятельное удаление аккаунта и выпуск новых персональных API-токенов (PAT) доступны только через обычную веб-сессию пользователя с установленными проверками. Пользовательские интеграции через PAT/OAuth не могут выполнять эти действия через REST или MCP; scopes, владение компанией и роль TENANT\_ADMIN не отменяют запрет. Веб-сессия после социального входа является обычной веб-сессией; OAuth-разрешение AI-клиента является интеграционным доступом. Это ограничение интеграций не меняет штатные сценарии регистрации/восстановления пароля и существующие правила протокольного OAuth refresh/revoke. Обновление OAuth-токена не означает выпуск нового PAT. Административный доступ через интеграции — D223; компании — D224, уровни доступа — D225; глобальные аккаунты — D226, выдача/расширение разрешений — D227; частичный возврат подписки исключён D228.

D223 — в первой B2B-версии GLOBAL\_ADMIN разрешена работа через PAT, OAuth и MCP с отдельными явно выданными административными разрешениями. Для административной операции требуются актуальная роль GLOBAL\_ADMIN и действительное административное разрешение на эту операцию; одного пользовательского токена/гранта и наличия роли недостаточно. Обычные пользовательские PAT/OAuth не получают административные полномочия автоматически и сохраняют границы D219–D221. В пределах выданного административного разрешения действуют полномочия B02; аутентификация, проверка scopes, отзыв и внутренний аудит сохраняются. Запрет GLOBAL\_ADMIN через PAT из прежнего релиза не является целевым B2B-контрактом. Область по компаниям/платформе определяет D224; уровни чтения/изменений — D225, глобальные аккаунты — D226, выдача/расширение разрешений — D227; частичный возврат подписки исключён D228. D223 не выдаёт неограниченный grant.

D224 — административное PAT/OAuth-разрешение GLOBAL\_ADMIN выдаётся на явно выбранные компании; доступ ко всей платформе доступен только отдельным явным выбором. Пустой или отсутствующий список компаний не означает доступ ко всем. Это область конкретного разрешения, а не ограничение самой роли: роль не позволяет выйти за область предъявленного PAT/OAuth. REST/gRPC/MCP, поиск, списки, агрегаты и пакетные операции проверяют эту область; OAuth refresh и MCP-сессия не расширяют её. Добавление компаний или переход к доступу ко всей платформе требует явного выбора в веб-сессии GLOBAL\_ADMIN по D227. UI показывает выбранные компании либо доступ ко всей платформе. Разрешённые операции проверяются отдельно: доступ ко всей платформе сам по себе не даёт права на любые действия; уровни доступа — D225, глобальные аккаунты — D226, выдача/расширение разрешений — D227; частичный возврат подписки исключён D228.

D225 — административное PAT/OAuth-разрешение имеет два уровня: «только чтение» и «чтение и изменения». Оба ограничены областью D224. Уровень чтения не разрешает создавать, изменять или удалять бизнес-данные и выполнять административные действия с изменением бизнес-состояния; роль GLOBAL\_ADMIN не отменяет это ограничение. Проверка действует в REST/gRPC/MCP по эффекту операции, а не только по HTTP-методу. Уровень «чтение и изменения» разрешает изменения в пределах выданных полномочий и области, не расширяя их. UI показывает выбранный уровень; повышение до изменений требует веб-сессии GLOBAL\_ADMIN по D227. Refresh и продолжение MCP-сессии сохраняют уровень. Служебный аудит и протокольное обновление токена не являются изменением бизнес-данных. Управление глобальными аккаунтами — D226; матрица операций/scopes следует D223–D227; частичный возврат подписки исключён D228.

D226 — интеграции GLOBAL\_ADMIN могут блокировать глобальные аккаунты пользователей, изменять их глобальные роли и удалять аккаунты. Одновременно требуются актуальная роль GLOBAL\_ADMIN, действительное административное PAT/OAuth-разрешение с уровнем «чтение и изменения», отдельное право на управление глобальными аккаунтами и область «вся платформа», выбранная явно по D224. Список выбранных компаний, включая все текущие компании пользователя, не заменяет область «вся платформа». Уровня изменений или области всей платформы без отдельного права недостаточно. Те же условия действуют при вызове через MCP и при исполнении доменной операции. Обычные пользовательские интеграции сохраняют ограничения D221. UI явно показывает право управления аккаунтами; внутренний аудит и требования целостности сохраняются. Выдача и расширение административных разрешений доступны только через веб-сессию GLOBAL\_ADMIN по D227.

D227 — выдавать новые административные PAT/OAuth-разрешения и расширять существующие можно только через обычную веб-сессию текущего GLOBAL\_ADMIN с установленными проверками. Административные интеграции через PAT/OAuth и MCP не могут выдавать такие разрешения или повышать их область, уровень либо специальные права, даже имея доступ ко всей платформе, уровень изменений и право управления глобальными аккаунтами по D226. Обмен OAuth-кода по уже одобренному веб-сессией разрешению сохраняется без расширения прав. Штатный OAuth refresh остаётся доступен в пределах ранее выданного действительного разрешения с проверкой актуальных прав и отзыва; refresh не создаёт новое разрешение и не повышает полномочия. Выдача нового PAT не является refresh. UI и API различают выдачу/расширение и протокольное обновление; запрет проверяется на сервере, а не только скрытием элементов UI/MCP. Существующие правила отзыва и внутреннего аудита сохраняются.

Публичная регистрация off закрывает самостоятельное создание identity, но сохраняет вход существующих, восстановление и согласованное принятие приглашения новой identity. Social login off закрывает новые внешние auth flows, email/password и имеющиеся веб-сессии остаются; уже принятый flow завершается с проверкой state. Новый social аккаунт не обходит signup off. Social login и OAuth AS для MCP — разные возможности.

Trusted actor/target tenant/project и scopes проверяются на каждом доменном пути и потребителе. Членство обычного пользователя в одной компании не открывает другую; GLOBAL\_ADMIN имеет явное полномочие, а не неподписанный bypass. Секреты/токены/платёжные credentials не возвращаются в публичном flags API. Версия/capability и причины отказа согласованы между UI/API/MCP/jobs.

D237: возврат нераспределённой банковской переплаты — отдельная согласованная операция B09/B10; оплаченная подписка сохраняется. D228 исключает частичный возврат платы за подписку.

D240 — в первой B2B-версии двухфакторная аутентификация обязательна для веб-входа GLOBAL\_ADMIN. Одного успешного первого фактора недостаточно для завершённого веб-входа и административной веб-сессии. До успешного второго фактора административный веб-доступ не предоставляется; пропуск или неуспешная проверка его не открывают. Полномочия GLOBAL\_ADMIN по B02 не отменяют требование аутентификации. Выбор другого поддерживаемого способа веб-входа не должен обходить это требование. Выдача новых и расширение административных PAT/OAuth-разрешений по D227 требуют полноценной веб-сессии GLOBAL\_ADMIN с выполненным D240. Область этого решения — веб-вход; административные PAT/OAuth/MCP и протокольный refresh продолжают следовать D223–D227, интерактивная проверка второго фактора при каждом интеграционном запросе этим решением не вводится. Способ, роли, первичное подключение и восстановление уточнены D242–D245; дополнительные проверки transfer/bank-confirm/refund определены D248; удаление аккаунта при ограничениях компаний определено D249. Приёмка: успешный веб-вход с обоими факторами; незавершённая или неуспешная проверка второго фактора не открывает административные действия и не позволяет выдать/расширить административное разрешение. Сценарии email-кода и операторского восстановления реализуются по D242/D245 и принципу D229.

B13. Уведомления
----------------

*Решения: D35, D37, D39, D40, D107, D108, D109, D110, D118, D119, D160, D182, D183*

Обычные email, Telegram и inbox независимы и управляются глобальными флагами/личными настройками. Telegram требует привязки и согласия; уведомления, созданные при выключенном Telegram, после включения не отправляются накоплением (TAS-391). Обычный inbox off не удаляет историю и не отключает другие каналы.

Уведомления владельцу о новых цене/лимитах и напоминание о банковском продлении обязательны одновременно по email и внутри Taska, несмотря на обычные opt-out. Доставка по каналам отслеживается отдельно, retry не выдаётся за успешную отправку и не дублирует бизнес-событие. Сбой email не отменяет созданный inbox.

Приглашения, безопасность и коды подтверждения не являются обычными task notifications. Актуальные права получателя обязательны; события/ошибки/уведомления не раскрывают чужие проекты или данные бывшему владельцу. Будущие сообщения не отправляются прежнему owner по устаревшему кэшу.

B14

B14. Глобальный профиль и удаление аккаунта
-------------------------------------------

**D249 — решение владельца от 02.11.2026.** Самостоятельное удаление глобального аккаунта разрешено, даже если одна из оставшихся компаний на паузе владельца, заблокирована платформой или имеет открытый банковский спор. До исполнения пользователь не должен владеть ни одной компанией и нигде не должен быть последним активным TENANT\_ADMIN. После проверки и отдельного кода удаления автоматически прекращаются его остальные участия по B14. Ограничения компаний не блокируют эту личную операцию и не снимаются ею; данные компаний и финансовые факты сохраняются. Это правило удаления аккаунта, а не удаления компании по D244.

*Решения: D165, D166, D167, D202, D203, D204, D205, D206, D207, D226*

Один displayName и один аватар аккаунта для всех компаний. Tenant-specific имён/аватаров нет. Аватар вне tenant storage quota, max 2 МБ; удаление одной компании не удаляет профиль других членств. TENANT\_ADMIN не редактирует чужие глобальные credentials/профиль; GLOBAL\_ADMIN имеет административный доступ.

Самостоятельное удаление аккаунта: сначала передать/удалить все собственные компании, а в остальных не оставаться последним активным TENANT\_ADMIN. FREE-компанию нельзя передать; её удаляют отдельным подтверждённым действием. Проверяются все memberships, а не выбранный контекст.

Удаление аккаунта подтверждается отдельным одноразовым кодом из подтверждённой почты либо заранее привязанного Telegram. Purpose/account/version/expiry/single-use не позволяют использовать код удаления компании. Проверки owner/last-admin повторяются при исполнении.

После выполнения условий автоматически прекращаются остальные ACTIVE/SUSPENDED memberships, освобождаются места, отзываются доступы и отправленные администратором приглашения, снимаются назначения. Задачи, комментарии и действия истории остаются. В обычной истории/API/экспорте автор — «Удалённый пользователь», без старых имени/аватара/email; старые author snapshots не обходят отображение. Произвольный текст комментариев автоматически не переписывается этим правилом. Новый account с тем же email не получает старые права/авторство.

Финансовые документы и внутренний аудит имеют отдельную политику хранения; не фальсифицируются удалением профиля. FREE-used marker — B04; механизм и retention оформляются до запуска.

Административные блокировка аккаунта, изменение глобальных ролей и удаление через PAT/OAuth/MCP разрешены D226/B12: актуальный GLOBAL\_ADMIN, отдельное право управления аккаунтами, уровень изменений и явно вся платформа. Выбранных компаний недостаточно.

B15

B15. Проекты, workflow и доменные данные
----------------------------------------

*Решения: D09, D10, D27, D30, D32, D52, D105, D106, D111, D112, D113, D125, D126, D127, D128, D177, D181, D196, D222*

TENANT\_ADMIN создаёт проект при доступном лимите/флаге; автоматически управляет всеми проектами своей компании. Project ADMIN управляет своим проектом и добавляет существующих активных участников компании. GLOBAL\_ADMIN обладает полными административными правами. Архив сохраняет данные и занимает проектную квоту; безвозвратное удаление с подтверждением освобождает квоту по завершённому lifecycle.

Workflow и типы задач изолированы проектом/компанией. Пользовательская настройка доступна FREE и paid при своих флагах; выключение конфигурации не останавливает задачи по существующему графу/типам. Общие шаблоны не становятся изменяемым состоянием чужой компании.

Комментарии, связи, watchers, labels, worklogs и задачи проверяют доступ к своим данным и обоим концам ссылки; отдельные флаги для этих core действий не введены. Секретные/raw private payload не дублируются в history/outbox. История удалённого аккаунта — B14.

D222 — перенос проекта между компаниями отложен до отдельного этапа для всех ролей, включая GLOBAL\_ADMIN. В первой B2B-версии такая функция отсутствует; полные административные права не создают исключение для переноса. Проект сохраняет компанию, в которой создан. Смена владельца самой компании является другой, ранее согласованной операцией.

B16

B16. Файлы и ресурсный учёт
---------------------------

*Решения: D99, D100, D123, D124, D137, D138, D139, D140, D141, D142, D166*

Attachments принадлежат задаче/проекту/компании; глобальный аватар принадлежит аккаунту и исключён из всех tenant quotas. Логотипов компании нет. Ограничения размеров и storage — B05.

Upload reservation и confirm однократны, фактический размер/тип проверяются сервером, выдача/download/cleanup учитывают права. Неудачный S3 delete не делает отрицательный usage; orphan cleanup работает по своему manifest. Удаление компании не должно затронуть общий аватар аккаунта.

Upload flag off запрещает новые загрузки/замены; существующее разрешённое скачивание сохраняется, принятую операцию завершают по согласованному lifecycle. READ\_ONLY из-за storage не добавляет право удалить отдельное вложение; проектная очистка остаётся отдельным действием. GLOBAL\_ADMIN — административное исключение с реальным учётом.

B17

B17. Экспорт и удаление компании
--------------------------------

*Решения: D26, D30, D34, D36, D101, D102, D143, D168, D169, D170, D174, D178*

Экспорт доступен FREE/paid. TENANT\_ADMIN выгружает все рабочие проекты/задачи/файлы своей компании; обычный участник — только доступные ему данные. Финансовые документы исключены из общего рабочего архива даже у owner, доступны отдельно по финансовым правам. Credentials/секреты не экспортируются.

При финансовом READ\_ONLY экспорт допускается по правам; при owner pause/platform block — когда разрешено чтение. Export flag off блокирует новые jobs, но готовые можно скачать по актуальным правам. Если чтение закрыто, старый готовый архив не обходит запрет. GLOBAL\_ADMIN имеет свои административные полномочия.

Готовый архив хранится default 24 часа от первого READY, настраиваемо. Download/retry не продлевают expiry; старые ссылки не переживают срок, поздний physical cleanup не открывает доступ. Удаляются только производные архивы, не исходные данные.

Компания удаляется владельцем без возможности отмены/корзины, с двойным UI-подтверждением и одноразовым кодом из подтверждённой почты либо ранее привязанного Telegram. При финансовом READ\_ONLY из-за неоплаты/квот это разрешено. Полномочия GLOBAL\_ADMIN отдельны. Не удалять другие компании/глобальные аккаунты; FREE-возможность не восстанавливается. Финансовые факты/audit и их доступ после удаления требуют формализованной политики.

B18

B18. Технические и приёмочные границы
-------------------------------------

*Решения: D229, D237*

Архитектурная база: сервисные владельцы БД, WebFlux/R2DBC, trusted TenantContext, явные SQL predicates + RLS, scoped jobs/service identities, transactional outbox. Публичный REST — статический OpenAPI; gRPC — proto; подписанные данные актёра и scope не доверяют клиентскому role. Глобальные identity/аватар отличаются от tenant-owned данных. Административный доступ не должен превратить обычный запрос в межтенантную утечку.

Изменения бизнес-матрицы требуют обновить REST/gRPC/MCP, jobs/cache/events, UI, SQL/RLS assertions и тесты. Миграции схем остаются нужны, backfill старых тестовых данных — нет. UserInitializer для GLOBAL\_ADMIN сохраняется; demo USER default off.

D229 — критерии приёмки и тесты описывают позитивные и негативные пользовательские сценарии поддерживаемых функций. Негативный сценарий должен иметь реальный путь запуска: например, запрос без необходимых прав, невалидный ввод или недопустимое текущее состояние существующей операции. Для функций, исключённых из релиза и не имеющих пути вызова, отдельные тесты не создаются; граница функционала фиксируется в постановке. Не придумывать endpoint/команду отсутствующего частичного возврата оплаты подписки ради проверки отказа. В поддерживаемых сценариях проверяются результат и сохранность состояния; реальные повторы, конкурентность и сбои платежей/лимитов проверяются по пользовательскому потоку. \*IT запускать явно. Проверки на final head после нейроревью; E2E сценарии/код в Git, результаты/секреты вне Git. Эта ревизия не выполняла продуктовые E2E и не подтверждает deployment.

Release gate: чистый старт, два tenant, обычные роли + GLOBAL\_ADMIN, сроки/fake clock, счета/возвраты/споры, приглашения, приватность файлов/экспорта/профиля, UI и реальные launch dependencies. Бизнес-запись в Jira не закрывает техническую реализацию и не разрешает автоматический rollout.

D237 — возврат нераспределённой банковской переплаты входит в согласованный функционал; для него нужны реальные сценарии возврата с сохранением оплаченной подписки по B09/B10.
