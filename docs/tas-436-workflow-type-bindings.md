# Типы задач и workflow — TAS-436

Новый тип `POST /api/v1/projects/{projectId}/issue-types` принимает необязательный UUID `workflowId`. Без него используется workflow первого типа в реестре (`sortOrder`, затем `code`); это основной workflow проекта. Явно можно выбрать свой workflow проекта, в том числе сохранённый без типов, либо общий default. Ответ создания остаётся плоским объектом типа и содержит `workflowId`; общий DTO реестра и MCP `get_project` не расширяются этим полем. Ошибка привязки до её фиксации не публикует тип в реестре.

`POST /api/v1/projects/{projectId}/workflows` может забирать типы из другого собственного workflow или default. Поле `statusMappings` сопоставляет старые ключи статусов с целевыми. Ответ — прежний `ProjectWorkflowDto`, HTTP 201.

`PATCH /api/v1/projects/{projectId}/workflows/{workflowId}` с `issueTypes` заменяет полный набор типов:

```json
{
  "version": 7,
  "issueTypes": ["TASK", "EPIC"],
  "statusMappings": {"BACKLOG": "TODO"}
}
```

Добавленные типы переходят в редактируемый workflow, убранные — в общий default, даже если основной workflow проекта другой. У запроса с `issueTypes` обязательна ожидаемая `version`; конфликт — 409. Правка только имени сохраняет прежнюю необязательность версии. Отсутствующее `issueTypes` не меняет привязки; явные null, дубликаты и неизвестные типы запрещены. Пустой целевой набор отклоняется с `WORKFLOW_ISSUE_TYPES_EMPTY`.

Если перенос забрал последний тип у другого собственного workflow, его граф и владелец сохраняются. Он виден в списке с пустым `issueTypes`, может получить типы повторно или быть удалён. Общий default не изменяется. Версии затронутых собственных workflow увеличиваются один раз; новый workflow начинает с версии 1.

## Статусы задач

Статус сохраняется, если допустим в целевом workflow; явное сопоставление имеет приоритет. При отсутствии подходящего сопоставления возвращается `WORKFLOW_ISSUES_UNMAPPED`: `issueCount`, `statusKeys`, `targetStatusKeys`. У добавленных и убранных типов разные назначения: сопоставление проверяется для фактического целевого workflow каждой задачи. `targetStatusKeys` содержит общие допустимые ключи для проблемных назначений; этот список может быть пуст. Дополнительные `targetStatusKeysByIssueType` и `statusKeysByIssueType` содержат JSON-объекты в строках details и уточняют назначения по типам.

Лимит `WORKFLOW_MIGRATION_LIMIT` — суммарно 5000 задач, которым нужно изменение или сопоставление статуса. Уже допустимые неизменяемые статусы и identity-сопоставления не расходуют лимит. Soft-deleted задачи не меняются. Каждое фактическое изменение статуса увеличивает версию задачи и создаёт одну запись TRANSITIONED и одно событие ISSUE_TRANSITIONED по прежним правилам уведомлений. Остальные поля, наблюдатели и тип задачи сохраняются. В публичной истории доступны автор и канал действия, без имени/UUID токена и UUID операции.

При создании задачи всегда проверяется фактический начальный статус, включая неявный TODO. Если основной workflow не содержит TODO, запрос без `statusKey` отклоняется с `STATUS_NOT_IN_WORKFLOW` без записи задачи; явно указанный допустимый статус разрешён и у графа без видимых переходов. Эта проверка использует только нужные типы и не загружает все графы проекта.

Новые команды создания/правки workflow допускают JSON до 1 МиБ; больший запрос — 413. Лимиты других DTO не увеличиваются. Отдельный `WORKFLOW_BINDING_PLAN_TOO_LARGE` отклоняет внутренний план, который не помещается в транспорт; операцию следует разбить. Это не меняет предел числа задач.

## Сбои, повторы и выкатка

Это восстанавливаемая операция между независимыми БД. Workflow-service сначала сохраняет неизменяемый план, project-service резервирует поколения типов, issue-service одной транзакцией меняет статусы/history/outbox и сохраняет receipt, затем workflow-service фиксирует привязки и версии. После APPLIED операция доводится вперёд; временная недоступность не вызывает обратного переноса задач. Создание типа использует скрытый intent в project-service: поколение публикуется только после атомарной привязки и receipt в workflow-service. Запоздалая отменённая команда не может заново занять резервирование или применить перенос.

При неопределённом исходе внешний запрос возвращает 503 `WORKFLOW_BINDING_CHANGE_PENDING` либо `ISSUE_TYPE_CREATION_PENDING`. До завершения операции действуют fences для создания, PATCH и переходов задач и для зависимых от графа чтений/правок. Обычные ошибки доступа к незавершённой операции не раскрывают её UUID. Recovery workers продолжают операции после восстановления зависимых сервисов, сохраняя исходного автора и канал. После issue commit завершение не зависит от последующего отзыва роли автора.

Для восстанавливаемых команд заранее сформировать и сохранить `X-Request-Id`. При 503 повторять тот же запрос с тем же заголовком. Тот же ключ с другим телом возвращает 409; исправление сопоставления после окончательного 400 — новая команда и новый ключ. Новый POST workflow с новым ключом может создать ещё один workflow: имя не уникально. Публичный повтор заново проверяет текущие права. Незавершённые журналы и receipts не очищаются по TTL, fences вручную не снимать.

Нужна согласованная выкладка project-service, workflow-service, issue-service и gateway с новыми RPC и миграциями. Все писатели должны учитывать резервирования. Старое RPC миграции статусов теперь требует реальную ожидаемую версию исходного workflow; issue-service проверяет актуальные привязку и версию, чтобы поздний старый запрос не применился после переноса типа. Общая таблица project reservations обратно заполняется из журнала TAS-433; старые changesets не меняются. Графы с однозначными историческими bindings получают владельца; старый граф без доказуемого владельца не становится доступным произвольному проекту.
