# Работа агента в Taska backend

Начните с [README](README.md), затем откройте [карту разработки](docs/agents/README.md).
Подробный процесс и проект harness: [спецификация](docs/agents/harness-spec.md).
Команды и выбор тестов: [матрица проверок](docs/agents/verification.md).

## Перед изменениями

- Прочитайте задачу и применимые инструкции. Зафиксируйте ожидаемое поведение и критерии приёмки. Явные указания пользователя определяют область работы; эта документация не даёт самостоятельного разрешения на merge или deployment.
- Проверьте `git status`, текущую ветку, актуальность `origin/develop` и связанные PR. Сохраняйте чужие изменения. Для новой задачи используйте отдельную `codex/TAS-<номер>-<описание>` от актуального `develop`.
- Сведения из старого чата, Jira, Confluence и личных skills проверяйте по текущему коду. Различайте реализованное, проектируемое и фактически развёрнутое.
- До выбора задач уточняйте их актуальную свободу и зависимости. Tenant/B2B-функционал не включайте без явного поручения.

## Источники истины и ограничения

- Публичный REST: `api-gateway/src/main/resources/static/openapi.yml`. `/v3/api-docs` публикует тот же контракт; `/v3/api-docs/generated` — справочная генерация.
- gRPC: `grpc-common-lib/src/main/proto/v1/`; не редактируйте сгенерированные stubs. Для схем БД читайте миграции владельца данных. Применённые Liquibase changesets не переписывайте.
- Java release — 21 из `pom.xml`; PR CI использует JDK 25. Это разные параметры. Не меняйте уровень языка для исправления локального окружения.
- Сохраняйте реактивную модель WebFlux/R2DBC, границы сервисных БД и transactional outbox. Изменение общего контракта требует проверки потребителей.
- Проверяйте project ACL отдельно от глобальной роли. Не выводите доступ из одного `GLOBAL_ADMIN`. Не раскрывайте токены и текст приватных данных через события, ошибки или логи.

## Проверка и завершение

- Выберите проверки по [матрице](docs/agents/verification.md). Обычный `verify` не выбирает классы `*IT`; запускайте необходимые IT явно и проверяйте, что тесты действительно выполнились.
- Для изменения поведения добавляйте содержательные проверки успеха, отказа и сохранности состояния. Для документации проверяйте ссылки, команды и соответствие коду.
- Отдельный PR на задачу. Описывайте результат, совместимость, выполненные проверки и ограничения. Проверяйте нейроревью на актуальном PR head и открытые замечания; зелёный job сам по себе не подтверждает корректность.
- После финальных исправлений и ревью повторите применимые E2E на проверенной версии. Изменение head обесценивает затронутые проверки. Невыполненный сценарий отмечайте как пробел, а не как успех.
- При merge учитывайте явное разрешение пользователя, текущие required checks и отсутствие нерешённых блокирующих замечаний. `develop` автоматически запускает deployment стенда, включая документационные изменения.

## Стенд, данные и передача работы

- Используйте только согласованную среду и свои фикстуры. Не сбрасывайте общие БД, квоты и блокировки, не подменяйте сервисы и не перезапускайте общий стенд ради теста без разрешённой области действий.
- Секреты получайте через настроенные подключения или внешнее хранилище. Не печатайте raw env, токены, cookies, invitation links и presigned URL. Существующий `.env` не перезаписывайте.
- В Git хранятся [E2E-сценарии](docs/testing/backend-e2e-scenarios.md) и код проверок. Результаты прогонов, журналы, credentials и состояние фикстур храните вне Git; `target/` подходит для локальных временных файлов. Ошибки продукта оформляйте в Jira с санитизированными шагами.
- При разрешённой параллельной работе используйте отдельные worktree/ветки и собственные фикстуры. Согласуйте владельца общего контракта. Передавайте SHA, изменённые контракты, выполненные проверки и оставшиеся ограничения; не переносите секреты.
