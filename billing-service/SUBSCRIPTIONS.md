# Subscription model — TAS-314

Implemented alongside the [catalog](README.md), using [BillingService](../grpc-common-lib/src/main/proto/v1/billing-catalog.proto). This is the tenant-scoped subscription/coverage model, not invoice issuance, payment processing, calendar calculation or plan-change policy. Those inputs belong to TAS-475/476/331/352/354. Gateway REST and production trust activation remain separate.

## Stored model and migration

[0002-subscriptions.sql](src/main/resources/db/changelog/0002-subscriptions.sql) appends to the existing catalog changelog; applied 0001 remains unchanged. Dedicated app/deployer/migrator roles and FORCE RLS apply to all three new tables.

- `subscriptions`: one row per tenant, selected plan UUID and immutable selection snapshot, internal FREE/AWAITING_PAYMENT/PAID mode, version, current pointer, original anchor, scheduling and autopay metadata. Selecting PAID creates AWAITING_PAYMENT, with no FREE fallback or paid period. Initialized autopay is DISABLED; renewal cancellation is a separate concept. Mutations of renewal/plan/owner policy are not exposed here.
- `subscription_periods`: immutable tenant/invoice/source financial fact/plan/activation identity, UTC `[starts_at,ends_at)`, original day/time anchor, plan terms snapshot, source PSP/WIRE and `confirmed_at`. Status alone may transition GRANTED → REVOKED or SUPERSEDED. Dates, financial provenance and terms cannot be rewritten; history cannot be deleted through normal DML. Overlap is deliberately allowed. Tenant+invoice and tenant+activation operation are unique, preventing a second period for a repeated settlement or a PSP/WIRE race.
- `subscription_command_receipts`: tenant/action/key/requestHash, exact protobuf response and issuer/optional actor. This separate scoped receipt permits a legitimate SERVICE principal without inventing a human actor UUID or fake global tenant. Receipt replay still requires current verified service authority. These are financial/idempotency metadata; production retention integration is subsequent work.

The current-period FK is composite `(tenant_id,current_period_id)`. The actual invoices table is introduced by TAS-475: **that migration must add** `(tenant_id,invoice_id) → invoices(tenant_id,id)` on periods before enabling invoice settlement. No fake invoice/financial-fact table is created to satisfy a forward FK. Until authoritative evidence adapters exist, settlement is fail-closed. Financial facts/invoices and periods reside in the same billing database; future settlement must use the supplied transaction connection, preserving atomicity.

## Internal commands and evidence

`SubscriptionStore.initialize(tenant,plan,key)` accepts only the verified `initializeSubscription` SERVICE purpose from `tenant-service`, tenant-bound with write scope. It selects a current published catalog offer and serializes creation by PK. Concurrent creates for the same plan produce one subscription; a different plan is a conflict, not an implicit plan change. Same-key retries replay the original response.

`grant(tenant,evidenceId,key)` requires `applySubscriptionCoverage` from `billing-service`. The evidence ID is resolved by the mandatory `SettlementEvidenceAuthority.confirmed` inside the same tenant transaction. There is no public mutation RPC accepting client `paid=true`, a browser redirect or caller-supplied timestamps as proof. Missing evidence returns PAYMENT_PENDING; a missing/unavailable adapter returns DEPENDENCY_UNAVAILABLE without writes.

Positive evidence is a fully confirmed, invoice-bound settlement decision, including tenant, original source financial fact, plan UUID, activation operation, starts/end, original UTC anchor, PSP/WIRE and confirmation time. TAS-331 computes the calendar period and TAS-352 validates full allocation; TAS-354 decides any explicit superseded period IDs. The model checks shape/scope, a published PAID version, unique invoice/operation, and supported PostgreSQL microsecond precision. It copies immutable catalog terms for the referenced invoice version, including a historical published version: a newly published catalog never reprices this paid snapshot. Superseding foreign/non-GRANTED period IDs fails and rolls back the entire operation. A future-starting period cannot supersede current coverage early: an explicit supersede is permitted only when the replacement has started.

A subscription row lock serializes coverage changes. Same-invoice replay with identical provenance is a no-op even under another delivery key; incompatible provenance conflicts. A revoked/superseded period is never re-granted by replay. The period, subscription version, durable response and outbox event commit together. `TenantTransactionExecutor` joins an already owned settlement transaction on the same physical connection; an outer rollback also removes period/version/receipt/outbox effects.

`revoke(tenant,evidenceId,key)` requires `revokeSubscriptionCoverage` from `billing-service` and a final `SettlementEvidenceAuthority.reversed` result. For full refund/final chargeback, including D251 LOST_PARTIAL_COVERAGE_REVOKED, it revokes the **whole** GRANTED coverage linked to that exact tenant+invoice+source financial fact and disables its subscription autopay. It neither calculates a proportional remainder nor creates money/refund facts. Independent periods are unchanged. Repeated or unrelated reversal has no additional version/outbox effect. If no independent paid coverage remains, a new full confirmed payment/activation creates a new period; old remaining days are not carried over.

The production default adapters deny access/unavailable; test fixtures supplying positive evidence are not live settlement implementations. The calendar/settlement adapter contract, not an environment flag or caller role, is responsible for primary invoice validation, actual PSP success/WIRE confirmation time, late-payment eligibility and final reversal provenance.

## Read semantics and rights

`GetSubscription` and `ListSubscriptionPeriods` require a verified tenant/action/read scope and a current `FinancialReadAuthority` decision. Ordinary WEB_TENANT/USER_PAT/USER_OAUTH additionally carry session/credential and membership generation. Only the ACTIVE current owner may read ordinary financial data; TENANT_ADMIN/project ADMIN alone is insufficient. Administrative web/integration access requires explicit applicable scope and READ/MODIFY, plus primary validation of the current GLOBAL_ADMIN/MFA/grant. A GLOBAL_ADMIN's USER credential retains ordinary rights. Each call and cursor page rechecks authority; the model never trusts an owner flag supplied in the request. Missing adapters fail closed.

The financial authority adapter must consult authoritative tenant ownership and membership, rather than a cached role inferred from a global account. RpcContextSecurity additionally verifies current keys, online authority, payload binding and mTLS peer. Neither global role nor a guessed UUID bypasses RLS. Get and list use the same transaction executor as other scoped billing work.

`GetSubscription` computes the current started GRANTED period from one SQL snapshot (preferring still-active independent coverage over expired history); future periods are not applied early. It does not depend on a scheduler updating a current pointer. Version identifies committed mutations; the derived view can switch at a paid boundary without a write. A future HTTP/cache adapter must expire at that boundary and cannot return 304 solely from this mutation version. The response plan/anchor follow that period. If no started GRANTED period exists, it returns the selected plan without inventing coverage. Reads never mutate a version or emit events.

`paidThrough` is an instant representing the **exclusive end** of the current paid coverage (TAS-504 A37). FREE and before-first-payment omit it. Expired GRANTED history retains its past end so callers can explain expiry; `now >= paidThrough` does not authorize paid access. Revoked/superseded coverage does not reappear. Owner pause/platform block do not rewrite these timestamps or prolong payment; independent restriction evaluation belongs to capabilities. Confirmed future renewals are visible in period history but do not advance the current period/limits before their start. The original anchor survives short months; calendar arithmetic itself is TAS-331.

History contains all statuses, newest `created_at,id` first, default50/max100. A versioned HMAC cursor uses the shared `BILLING_CATALOG_CURSOR_KEY`, a distinct subscription-purpose binding, tenant/actor/credential/session/generations/scopes/admin scope/page size, 15-minute TTL and subscription generation. A changed generation requires restarting the list. Header-preserving LEFT LATERAL distinguishes empty history from an absent subscription. Missing key disables listing, not the single-subscription read. No cursor carries raw credentials or financial document URLs.

## Verification and activation

```sh
python3 scripts/harness.py check --module billing-service
```

`SubscriptionIntegrationTest` is a required fresh nonempty report in the harness manifest. Its own PostgreSQL16 uses real app LOGIN/RLS and migration roles. It applies catalog0001 first, then upgrades through0002 and reruns migration, checking the original checksum and catalog rows. Coverage includes concurrent initialization/settlement/retry, conflicts, immutable snapshots/times/status, outer and outbox rollback, A/B FK/RLS, current-owner/admin scope denials, exact UTC boundaries and future renewal, source-targeted D251 revocation/new independent coverage, HMAC binding and real mTLS/JWS read RPCs. Existing catalog startup and contract tests remain required.

This proves the model and protected backend transports in isolated fixtures. It does not prove gateway REST, real PSP/WIRE reconciliation, invoice/financial ledger FK readiness, full calendar/plan-change policy, capability enforcement or deployed-stage B2B availability. Production enabling requires the authoritative adapters and the follow-up migration, not a permissive default.
